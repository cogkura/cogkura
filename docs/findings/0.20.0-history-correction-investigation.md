# Correction history after withdrawal: candidate fix

This is an uncommitted correctness candidate, not an approved change to the frozen retrieval contract. Its parent is Core 0.19.6 commit `9745201bfcc5410d678a07737a4c935dd294e5b4`, with the two previously investigated performance changes also present. The original failing evidence is retained in the [scaling investigation](0.20.0-scaling-followup.md).

## Root cause and behavior

A minimal reproduction needs one subject, an initial authoritative assertion, one later authoritative correction, and a later withdrawal of that correction. When an earlier `as_of` precedes the correction, the expected visible assertion is the original, with neither the future correction nor the future withdrawal visible. Both 0.19.6 and the initial 0.20 candidate instead raised `ValidationError` while scoring a future episode. Inspection also showed that, after excluding that episode, the future semantic successor could reach scoring.

When a correction successor was closed by a later edit, `_closed_snapshot` rebuilt a snapshot from the current memory but discarded the successor's incoming `correction` and `knowledge_at`. The stored predecessor's `closed_by` still identified that successor and the original correction's effective and knowledge times. Once the incoming link was lost, historical projection could no longer identify the corrected successor as not yet known. A similar loss could occur when a successor was closed by another correction.

The candidate preserves incoming transition metadata when creating new closed snapshots. For already-written records, retrieval reconstructs a missing correction link **in memory only** if a complete supported snapshot has exactly one same-tenant predecessor with an explicit matching closure, matching slot and matching effective boundaries. Conflicting, ambiguous, incomplete or unsupported records are not repaired by inference. Semantic-slot inspection does this only when its bounded inventory is complete. The persistent history and public revision-list output are not rewritten; source inspection still reports incomplete inventories conservatively. The test exercises both newly written and simulated legacy snapshots through recall, context preparation and slot inspection, including `valid_at` later than `as_of`, as well as before/at correction and withdrawal boundaries.

This intentionally changes the formerly failing historical behavior. It cannot inherit approval from previous frozen candidates. Existing records without the corroborating predecessor closure cannot be reconstructed by this narrow rule; a broader data-repair policy would need its own design and evidence.

## Isolated validation and review required

The correction-only source patch over the 0.19.6 parent, including the two earlier optimizations, is retained [here](data/0.20.0-historyfix-source.patch), SHA-256 `3dc049e01af301786d7c830fd0537829672ce573eddcbe04b05643672acec27a`. The fixed [in-memory](data/0.20.0-historyfix-memory.json) and [SQLite](data/0.20.0-historyfix-sqlite.json) history-fixture runs return all expected values, including the formerly failing early knowledge-time query. A targeted test passes for memory, SQLite and PostgreSQL, including simulated older snapshots and source inspection. The full Core suite with a fresh disposable PostgreSQL 14.18 memory database passed: 1,038 passed, 6 skipped. One earlier full run reused a database left by prior tests and failed two storage-isolation tests; the fresh-database run passed and is the reported result.

Independent Bench compared this correction-only candidate with the preceding overlap-reuse candidate on Python 3.12.13 with the same seed. Three frozen correction queries changed: `ac-q-c17`, `ac-q-hist-at-withdraw`, and `ac-q-hist-before-withdraw`. They contain 19 changed fields: activation/score values and one correction-relation field. The aggregate frozen metrics and use signatures did not change. The [raw frozen report](data/0.20.0-historyfix-bench-frozen.json.gz), [query details](data/0.20.0-historyfix-bench-frozen-details.json.gz), and [exact before/after field and fingerprint comparison](data/0.20.0-historyfix-exact-differences.json) are retained. The raw frozen gate remains failing; no prior exception is applied.

In the four-backend comparison, these same three correction queries changed on each backend. Three `source_aware_metamemory_v1` queries also changed on each backend. In particular, `sm-withdrawn` now exposes both the correction and withdrawal transition event IDs where frozen ground truth expects only the withdrawal. This changes one source-attribution check, reducing source assessment accuracy from 191/191 to 190/191. This is a real failing independent gate, not a passing validation or an approved gold change. The [raw four-backend report](data/0.20.0-historyfix-bench-four-backend.json.gz) and the same exact-differences file retain the data. The prior candidate's known cross-backend support-order differences also remain. A separate design and explicit approval are needed to decide the intended source-transition contract and any candidate-specific frozen differences; neither Bench gold nor numerical tolerances have been altered.

Before the next performance change, five uninstrumented mixed-workload queries produced medians of 3.464 s at 1,000 observations in memory and 0.490 s at 250 observations on SQLite; the individual [memory](data/0.20.0-historyfix-perf-memory-1000.json) and [SQLite](data/0.20.0-historyfix-perf-sqlite-250.json) samples are retained. These are single-host observations, not p95 or controlled acceptance results.

The user selected “report both transitions” for source inspection in this investigation. That decides the intended behavior for the correction and withdrawal chain, but it does not change the released Bench gold or automatically approve every exact query, scoring or source-assessment difference for a later candidate. The existing raw source-attribution failure remains open for candidate-specific review.

A further regression writes a simulated legacy SQLite record, closes and reopens the database, and checks that recall and semantic-slot inspection recover the old knowledge-time view without rewriting the persisted snapshot. The subsequent admission optimization is independently measured and validated in the [admission findings](0.20.0-admission-lookup.md).
