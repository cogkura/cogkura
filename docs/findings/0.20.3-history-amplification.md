# 0.20.3 scoped semantic-history amplification

**Status: measured initial-Agent envelope accepted; compaction deferred.**
On 25 November 2026 the release owner directed that timestamp-only row counts
alone must not delay 0.20.3: first establish whether the rows are semantically
necessary and whether measured growth is acceptable. If both hold, retain the
existing implementation and defer compaction to a later Core version.

The [revision-depth probe](0.20.3-scoped-read-scaling.md) records 385 new
revision-history snapshots after 20 corrections and one withdrawal in one
project; 341 snapshots differ from the immediately preceding snapshot for the
same revision only in `updated_at`. The original history of all other subjects
remained unchanged in the corresponding SQLite audit. The workload grows the
logical database by about 2.54 MB, but is one synthetic workload, not a universal
growth rate.

In the in-memory semantic store, `apply_reconciliation()` constructs every
planned revision and current memory with the processing time and records a
snapshot for each. SQLite applies that logic to a hydrated store and persists
the resulting snapshots. This explains the repeated rows even when the only
logical field change is the timestamp. The same logical path is relevant to the
in-memory store; PostgreSQL must be independently checked before claiming the
same physical growth behavior.

Simply omitting the rows or leaving timestamps unchanged would change an
observable field and could affect historical reconstruction: the existing
projection and source-assessment logic consult `updated_at` to decide whether
earlier state needs to be loaded or marked incomplete. Any correction must
preserve the exact public current and historical objects, snapshot-order and
unavailable-state behavior, corrections and withdrawals, cross-backend results,
and support for existing persisted databases. It must also receive the design's
required review if cognitive behavior changes.

A diagnostic compression estimate on the additional 20-correction snapshots
found 332,746 bytes of semantic JSON and 1,069,848 bytes of revision JSON;
independently zlib-compressing each payload reduced those to 141,659 and 399,208
bytes respectively. This excludes database, index and compression-format costs,
does not remove repeated rows or establish long-term growth, and is not an
implementation recommendation or validated database migration. Compact delta
snapshots or compressed storage would require explicit format compatibility,
corruption handling, historical reconstruction and backend-parity validation.
No runtime behavior has been changed as part of this investigation.

## Are timestamp-only snapshots necessary?

`scripts/audit_timestamp_only_history.py` makes a disposable copy of the
20-correction SQLite fixture and deletes only history rows whose immediately
preceding snapshot for the same identity differs solely in `updated_at`.
For the focused run, deletion was limited to project 049's current semantic and
revision identities: 118 semantic-history and 349 revision-history rows were
removed. The unmodified database was retained. The script then uses public
`recall()`, `prepare_context()` and `resolve_provenance()` on both databases
for two queries at eight historical instants before, during and after the
correction sequence.

In 12 of 16 cases, complete public recall and assessment objects differed after
removal. In every case, complete recall objects matched after normalizing only
`memory.updated_at`; ranked identities/statements and scores, rendered text,
assessment signals and flags, and provenance all matched. Normalizing timestamp
fields in assessment representations also made those representations match.
Thus, in this fixture, retaining or faithfully reconstructing the historical
`updated_at` values is necessary to preserve the existing complete public
results. The experiment does **not** prove every physical full JSON snapshot is
necessary: a lossless representation could potentially reconstruct the same
values. Nor does it establish equivalence across all histories, other public
inspection APIs, backends, or missing/corrupt snapshots.

The [final focused report](data/0.20.3-timestamp-removal-subject-final.json)
records all 16 checks and timestamps. An
[initial exploratory run](data/0.20.3-timestamp-removal-all-subjects-initial.json)
removed timestamp-only rows across all subjects; an
[intermediate focused report](data/0.20.3-timestamp-removal-subject-intermediate.json.gz)
retains the full assessment representations. None is a proposed migration or a
claim that deleting these rows is safe.

## Longer correction sequences

On independent copies of the same 90,353,664-byte baseline, the same workload
was extended to 50 and 100 successive corrections followed by one withdrawal
in project 049. The synthetic observation count remained 50 × 250. All
variants returned the expected incident, migration and historical evidence in
the top ten for project 000; its rendered context, assessment and recorded
ranked evidence matched the baseline. The five-sample preparation medians are
diagnostic only and are not candidate-acceptance p95 measurements.

| Corrections | Increase in logical bytes | New revision-history rows | Of those, timestamp-only | Preparation median |
| ---: | ---: | ---: | ---: | ---: |
| 5 | 552,960 | 70 | 56 | 0.579 s |
| 20 | 2,543,616 | 385 | 341 | 0.594 s |
| 50 | 9,273,344 | 1,690 | 1,586 | 0.643 s |
| 100 | 28,930,048 | 5,865 | 5,661 | 0.627 s |

The 100-correction variant increased the baseline logical file size by about
32%; both 50- and 100-correction audits preserved all pre-existing rows in the
three history tables and attributed every appended row to project 049. Growth
increased faster than the correction count in this particular sequence. The
fixture does not establish typical Agent correction frequency, available disk
budgets, retention policies, behavior across 50 simultaneously updated
projects, or a universal growth curve. It is therefore not sufficient on its
own to declare long-term storage growth acceptable or unacceptable for every
Agent deployment. On 25 November 2026 the release owner accepted this measured envelope for the
initial Agent and deferred compaction to a later Core version. This decision is
limited to the measured workload; it does not promise acceptable growth for
every deployment.
