# Retrieval scaling follow-up

This is an investigation of the uncommitted candidate described in [overlap reuse](0.20.0-association-overlap-reuse.md), not a release acceptance. The parent is `9745201bfcc5410d678a07737a4c935dd294e5b4` and the candidate `activation.py` SHA-256 is `5d1414dc120713b39192624ac1322591dede3a58645a6f38fc51503f11874f00`.

## Original 1,000-observation mixed workload

The unchanged `run_sqlite_workload.py --observations 1000 --revisions 5 --recalls 1 --mixed --uninstrumented` fixture was run sequentially across SQLite and in-memory, as in the original. The [candidate report](data/0.20.0-mixed-1000-after.json) records 1,006 observations, 5,006 observation revisions, 1,006 episodes and 1,006 semantic revisions, with all its logical parity checks passing. The single SQLite recall took 4.328 s; in-memory took 3.548 s. The [0.19.6 observation](data/0.19.6-uninstrumented-mixed-1000.json) recorded 82.73 s and 82.21 s respectively, also one recall each. The two observations use the same original fixture and host family, but the candidate used CPython 3.11.15 and the older run used 3.14.10; host state and process conditions were not controlled. This comparison indicates a large improvement but does not isolate the code change or establish a latency distribution. Both runs' fixture-level rounded ranked outputs and semantic and history hashes match; these do not replace exact frozen-output validation.

A separate [in-memory cProfile run](data/0.20.0-mixed-1000-after-profile.json) took 11.856 s wall / 11.744 s process CPU, including profiler overhead. `_authoritative_semantic_current_admission_identities` accounted for 9.052 s inclusive and its scored-result generator made approximately 1.50 million calls to `_result_identity`. The `rank_evaluated` inclusive total was 11.572 s. These are nested, overlapping times, not additive stages. Association fit was 0.416 s inclusive. This identifies a different dominant path for this fixture; it does not establish that it dominates other configurations or workloads.

The admission function iterates potentially relevant semantic candidates and performs a fresh linear search of `scored` for the first result with a matching identity. If S candidates reach that lookup and N results are scored, it can perform O(S × N) identity comparisons. A retrieval-scoped index of the *first* scored activation by identity is a plausible follow-up: it must preserve first-match behavior for duplicate identities, threshold handling, admission limits, stable ordering and exact scores. No implementation of that proposal is included in this investigation.

## Project-shaped fixture

The independent, small [software-project workload](../../scripts/run_software_project_workload.py) includes project architecture decisions, migration guidance, an incident and postmortem, tenant isolation, an integration relationship, and an authoritative correction. Its five narrow, broad and historical queries return ranked outputs and individual wall/CPU observations. The fixture is synthetic: copies repeat its narrative, it is not a representative coding-Agent corpus, and no quality gold or production capacity follows from it. A [one-project in-memory run](data/0.20.0-project-workload-memory-1.json) and [SQLite run](data/0.20.0-project-workload-sqlite-1.json) had nine episodes, six semantic revisions and one applied correction; the fixture's rounded ranked results matched for all five queries. At this size those samples are smoke tests, not scaling evidence.

Five additional uninstrumented, distinct queries were run per backend in fresh processes on CPython 3.11.15. The individual [SQLite observations](data/0.20.0-mixed-1000-sqlite-samples.json) were 4.229, 4.234, 4.200, 4.218 and 4.220 s (median 4.220 s); [in-memory](data/0.20.0-mixed-1000-memory-samples.json) was 3.554, 3.485, 3.590, 3.537 and 3.514 s (median 3.537 s). Fixture construction precedes each process's first query. The two processes ran sequentially, and neither host activity nor OS cache state was controlled. Five samples do not establish p95.

## Semantic history and a baseline correctness finding

The [history workload](../../scripts/run_semantic_history_workload.py) now checks both sides of a correction's effective boundary, a query before the correction was known, and optionally both sides of a withdrawal plus a query before it was known. Each version is observed and processed independently. It writes per-case status and returns a failing exit status if any expected value fails or recall raises; the expected results are not relaxed to make the run pass. Current and historical checks are subject-scoped, and further independently varied knowledge and effective times remain necessary.

With three subjects, three semantic versions and one withdrawal, `before_correction_known` raises `ValidationError: Memory reference cannot occur after the activation timestamp`. This occurs on the candidate's [in-memory](data/0.20.0-history-withdraw-candidate-memory.json) and [SQLite](data/0.20.0-history-withdraw-candidate-sqlite.json) backends, and on the released 0.19.6 baseline under the same CPython 3.11.15 runtime, both [in memory](data/0.20.0-history-withdraw-0196.json) and [SQLite](data/0.20.0-history-withdraw-0196-sqlite.json). All other cases in these reports returned the expected semantic value. In a diagnostic run, the failing candidate was the episode for `environment-0002`, created 2026-01-03 00:00 UTC, being scored at 2026-01-02 23:59:59.999999 UTC. This is a pre-existing historical correctness limitation, not an observed regression from the performance changes. It requires a separate root-cause investigation and fix with temporal and frozen-output validation; this performance investigation does not silently change that behavior or mark the case as passing.

A later [same-Python baseline run](data/0.20.0-mixed-1000-baseline-py311.json) used the released 0.19.6 distribution at `9745201bfcc5410d678a07737a4c935dd294e5b4` from the independent Bench environment via `PYTHONPATH`, with the same original script and CPython 3.11.15. Its installed runtime files were checked against the release commit, including `activation.py` SHA-256 `53c901dfa616da7d19cbea6602ff572bce2ec70eb9134977400044d863d90420`. One SQLite recall took 78.133 s and one in-memory recall took 76.505 s, compared with the candidate's single-sample 4.328 s and 3.548 s above. The original script's counts, ranked rounded outputs and semantic and historical hashes matched between these two runs. The runs were sequential rather than interleaved, host activity and filesystem caches were not controlled, and the baseline has one observation per backend; these numbers are observational, not a p95 or controlled production speed guarantee.

## Additional workload observations

The semantic-history fixture was run with 10 subjects and [one](data/0.20.0-history-memory-v1.json), [five](data/0.20.0-history-memory-v5.json) and [ten](data/0.20.0-history-memory-v10.json) processed semantic versions per subject, with matching SQLite runs for [one](data/0.20.0-history-sqlite-v1.json), [five](data/0.20.0-history-sqlite-v5.json) and [ten](data/0.20.0-history-sqlite-v10.json) versions. Those produced 10, 50 and 100 semantic revisions respectively; each reported all applicable current, historical, correction-effective and knowledge-time checks passing, and rounded ranked outputs matched between local backends. Withdrawal was disabled in these depth runs. Each query was observed once and scoped to one subject; revision depth also increases episodes and observations. These samples cannot establish revision-only complexity or p95. The separate withdrawal case above remains failing.

The project fixture was also run with ten synthetic projects: 90 episodes, 60 semantic revisions and ten applied corrections. On the [in-memory](data/0.20.0-project-workload-memory-10.json) and [SQLite](data/0.20.0-project-workload-sqlite-10.json) runs, all five queries' rounded ranked outputs matched. Individual query wall times ranged from 0.067–0.088 s in memory and 0.114–0.121 s on SQLite. These are single observations after fixture construction, and the project narratives are repeated; this does not establish quality, realistic scale or tail latency.

## Validation and status

The new workload and failure-reporting tests passed, as did offline locked dependency synchronization, Ruff, format check, mypy and the full Core suite (993 passed, 46 skipped). The history workload test verifies that the known withdrawal-sequence failure is reported and causes a nonzero exit; it is not a passing correctness result for that case. PostgreSQL was not re-run in this investigation; the prior candidate's scoped PostgreSQL and independent Bench results remain recorded in the [previous findings](0.20.0-association-overlap-reuse.md). No Core cognitive implementation was changed during this follow-up.

Before release, resolve the historical knowledge-time failure under a separately reviewed correctness change, validate the complete candidate against the unchanged frozen gold and all required backends, and run more representative controlled latency measurements. The proposed p95 target has not been ratified and is not established by these five-sample runs.
