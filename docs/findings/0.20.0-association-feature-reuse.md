# Retrieval-scoped association feature reuse: initial candidate

This is an uncommitted development candidate, not a release acceptance. Its Core parent is `9745201bfcc5410d678a07737a4c935dd294e5b4` (0.19.6). The measured candidate's `activation.py` SHA-256 is `f76cfa6de82bd7a0b533a7b15d6279a4bc11647860d5bb04865854689f8c712e`; the parent file's SHA-256 is `53c901dfa616da7d19cbea6602ff572bce2ec70eb9134977400044d863d90420`. The report's commit identifies the parent, not the uncommitted candidate. No release version or approval is implied.

The [investigation](0.20.0-retrieval-profiling.md) found `_associative_entity_fit` repeatedly constructs the same episode association features within a recall. The candidate lazily stores those immutable features by candidate object identity within a single semantic relevance context. Candidate references remain alive during the context, preventing identity reuse. It still evaluates every existing seed/episode pair and uses the existing overlap rules, sorting, bounds, paths and scoring. The cache is discarded after the retrieval; changes in data, time, tenant or configuration cannot reuse entries across calls. Empty feature sets are cached too. No cross-request cache, selective retrieval or cognitive formula changes are introduced.

## Measured observations

On the same host and Python 3.11.15 described in the investigation, the fixed mixed workload ran in fresh processes, sequentially, before and after the change. The first query follows fixture construction rather than a cold-device start. OS caches and host activity were not controlled. The five queries are fixed and distinct; no p95 is claimed. The original fixture records rounded scores and is not an exact acceptance fingerprint.

The feature-construction count fell from 48,500 to 100 at the 100-observation size and from 308,750 to 250 at the 250-observation size. Rounded ordered workload outputs match each corresponding retained baseline, including all five timed queries on each backend. Profiling adds overhead; profiled times must not be treated as uninstrumented latency. The measured improvement does not establish a production latency guarantee. In particular, the remaining seed/episode comparison loop still scales with semantic candidates, seeds and episodes and is a separate optimization opportunity requiring measurement and exact validation.

A regression compares the complete recall inspection against a run with feature reuse disabled on the same state and verifies that feature construction occurs again on the next retrieval. Existing historical, association, scoring and cross-backend tests remain relevant; they do not replace the independent release gate. The benchmark's existing small rounded-output parity check also does not establish exact historical or cognitive equivalence.

## Validation

On CPython 3.11.15, offline locked dependency synchronization, Ruff, formatting, mypy and the complete Core suite passed (989 passed, 46 skipped; PostgreSQL integration tests were not enabled). The direct feature-reuse regression also passed. No latency assertions were added.

An independent Bench diagnostic ran with CPython 3.12.13 and `PYTHONHASHSEED=0`, first using the installed released 0.19.6 distribution and then this dirty source candidate via `PYTHONPATH`. The installed baseline's tracked Python and SQL files were byte-for-byte equal to the parent commit. Across 22 frozen workload/profile runs, all 393 query fingerprints, complete retained query/use/metric signatures, and non-latency source metrics matched exactly between these two runs; diagnostics parity produced no mismatches in either. Timing metrics are excluded from equality. The [comparison summary](data/0.20.0-feature-reuse-bench-comparison.json), [baseline raw report](data/0.20.0-feature-reuse-bench-baseline.json.gz), [candidate raw report](data/0.20.0-feature-reuse-bench-candidate.json.gz), and their retained full-detail files record the evidence.

Both raw frozen comparisons report the existing `authoritative_corrections_v1/cogkura-correction` mismatch against the unchanged original gold. No old candidate approval was applied to this dirty candidate, and the same-environment equality above is not a strict frozen-gold pass. The harness's release gate also requires PostgreSQL, which was not run. A separate [exploratory mini backend run](data/0.20.0-feature-reuse-bench-mini-backends.json.gz) matched memory, SQLite and reopened SQLite, with no PostgreSQL. Larger workload coverage, all required backend/restart checks and exact candidate-specific release validation remain outstanding.
