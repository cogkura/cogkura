## Implemented behavior

- `assess_source_memory(context)` resolves selected primaries and included chunk
  members once, sharing exact-revision provenance reads. It separates evidence
  presence, revision resolution, optional locators, semantic relations, distinct
  source identity, and present-store revision currentness.
- `inspect_semantic_slot(SemanticSlotQuery(...))` reads bounded retained semantic
  inventory independently of activation/recall. It distinguishes known, contested,
  withdrawn, historical-only, unknown, and indeterminate state. There is no prose
  scan of unpromoted assertions or automatic abstention rule.
- Both built-in semantic stores implement optional `SemanticInspectionStore`.
  Custom stores without that capability return explicit unavailable/indeterminate
  diagnostics. Mandatory store and monitor protocols remain compatible; no
  migration or runtime dependency was added.
- Optional `SemanticDiagnosticsConfig` observes actual extraction, authority,
  qualification, deferral, reconciliation, and edit paths. Counters are unchanged;
  applied outcomes are returned only after storage succeeds. Reporting defaults
  off and performs no additional source-revision reads. Custom algorithms that
  cannot provide complete diagnostics are marked incomplete.
- Source independence stays `UNKNOWN`. Authority is an admission/operation
  declaration, not confidence, factual certainty, or a ranking feature.

Usage and contracts: [source-aware metamemory](../source-metamemory.md).

## Clarifications resolved during implementation

Semantic relation coverage applies only to semantic references requiring proven
support/contradiction relations. Direct episodic evidence is counted as not
applicable. Coverage is `None` when there are no semantic references. Omitted or
unknown applicable semantic relations make it `False`; omitting only episodic
references does not lower it. Exact revision and locator coverage remain separate.
Empty evidence is explicitly `has_evidence=False`.

Currentness counts describe examined evidence occurrences, with a separate
truncation flag so omitted references cannot appear completely assessed. Explicit
historical `as_of` queries mask present-store latest-revision comparisons. An
unprovable historical `projected_status` is `None`, and unsupported historical
classification remains indeterminate instead of exposing the present status.

Deduplicated pass records and legacy counters have different units. Records are
ordered using semantic and source identities; they do not create new decisions.
The existing withdrawal qualifier can defer the original target on replay even
while its durable state remains withdrawn. The new report preserves that branch
and counter rather than relabeling it `ALREADY_APPLIED`. A later pass's report is
not a durable unresolved-request ledger; history remains explicitly unavailable.

## PostgreSQL verification gap closed

The 0.18.2/Bench 0.3.10 PostgreSQL adoption/replacement/withdrawal/replay gap is now
**EXECUTED AND PASSED** for Core on local PostgreSQL **14.18 (Homebrew)**. Tests used
a disposable cluster under `/private/tmp` on port 55483, with a fresh memory
database for each Python runtime. All existing database fixtures were enabled,
including memory-admin migrations, the read-only source role, source-admin actions,
and same-database schema mode. No optional database tests were counted as passes
through skipping.

Execution uncovered two pre-existing backend defects:

1. `PostgresSemanticMemoryStore.apply_reconciliation()` wrote current derivations
   before inserting their referenced semantic revision, violating migration 006's
   foreign key on fresh adoption. The failure was reproduced with the unchanged
   `1a8bc04` source snapshot and an isolated test source namespace. Derivations now
   follow the revision insert within the same existing transaction. Reconciliation
   inputs, logical outcomes, and counters are unchanged.
2. The optional inhibition lower-bound expression `:after IS NULL` left PostgreSQL
   unable to infer the parameter type. Explicit `timestamptz` casts retain the
   same null/lower-bound filter semantics. No inhibition formula or behavior changed.

Database-enabled execution also exposed old test assumptions: migration expectations
omitted version 011 or expected only two versions after later migrations were
already present, and several cases reused source/subject identities across tests.
Expectations now preserve all installed migration records and test scopes are
isolated. No production source identity rule or migration SQL was changed.

Real backend comparisons cover adoption, replacement, future-effective boundaries,
historical reads, knowledge-time hiding, withdrawal and replay, source reports,
competing-edit decisions, tenant/subject isolation, bounded prefixes, and read-only
query counts. Coverage is for PostgreSQL 14.18; other PostgreSQL server versions
and stronger cross-store transaction isolation were not tested.

## Performance observation

A synthetic local probe stored 33 slots and inspected one target ten times through
PostgreSQL. Each inspection returned one revision and used **10 batched queries**;
median end-to-end time was **12.08 ms**, with a 10.19–24.22 ms observed range.
A deterministic integration test also verifies bounded target populations and
constant query counts with unrelated slots present.

`EXPLAIN (ANALYZE, BUFFERS)` on the small synthetic slot lookup selected a sequential
scan of `semantic_claims` and an indexed memory join using
`memories_tenant_id_memory_id_idx`. The existing tenant/slot index remains available;
a tiny-table sequential scan is not evidence that a new index is needed. No schema
change was introduced on the basis of this sample.

These numbers are an environment-specific observation, not a portable latency
budget or a production workload benchmark. Large snapshots, long histories, and
very large tenant inventories were not performance-benchmarked. Limits bound
returned populations, not JSON bytes or every derivation row loaded underneath.
The in-memory store still scans its retained inventory. PostgreSQL slot populations
share a read-only repeatable-read view, but later source/episode batches can use
separate stores; a fully atomic cross-store report is not promised.

## Retained limitations and next gate

- **Known 0.18.2 episodic prose limitation:** a later re-adoption episode can render
  its assertion even while the semantic fact remains withdrawn. This implementation
  preserves and documents the behavior; it adds no retrieval suppression redesign.
- No durable deferred-decision history, source independence inference, trust
  rankings, truth score, or automatic uncertainty/abstention policy.
- No complete bitemporal history or fabricated legacy authority/snapshot data.
  Historical status/attribution that cannot be proved stays incomplete/indeterminate.
- Exact slot queries accept finite scalar qualifiers; nested qualifier structures
  are not supported by the new query model.
- Independent CogKuraBench validation remains **PENDING** and separately authorised.
  The earlier 0.3.10 findings remain prior measurements. Its frozen authority,
  correction, recall, interference, and inhibition results must be checked in that
  subsequent validation release before 0.18.3 is declared fully validated.

The Core implementation is ready for review in one PR. No merge, release tag, or
package publication is part of this task.
