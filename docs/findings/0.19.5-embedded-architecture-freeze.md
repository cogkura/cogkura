## Core storage inventory and gates

All ten `storage/base.py` protocols have SQLite implementations and are wired into `EmbeddedMemory`: observation and checkpoint, episode, semantic and optional semantic inspection, activation, memory dynamics, learning, entity relationships, and inhibition. The existing SQLite storage, episode, semantic and cognitive store contract suites exercise these implementations; the embedded runtime tests cover reopening and the injected bundle. This inventory is implementation coverage, not by itself proof of all cross-backend behavior.

The full Core suite passed with PostgreSQL 16 on local macOS APFS on Python 3.11.15, 3.12.13 and 3.13.14: **1,030 passed without skips per runtime**. Each run used a clean memory schema and the repository's source fixture, with SQLite 3.53.1. The [hosted Core CI](https://github.com/cogkura/cogkura/actions/runs/43758147796) also passed the Linux/macOS/Windows and Python 3.11–3.13 matrix; PostgreSQL-specific cases were skipped there. Bench's suite including the new comparison test passed **318 tests** with PostgreSQL enabled against the source candidate. The four comparison datasets also passed dataset validation and Oracle smoke runs.

The initial independent SQLite Bench exploration is [retained](data/bench-0.19.5-embedded-exploratory.json). Its ID allocator was installed after Core was imported, so its reported seed did not control the UUID functions already bound by Core; its mismatches cannot establish behavioral differences. It is not a parity gate.

The subsequent [controlled comparison](data/bench-0.19.5-embedded-controlled.json) installs a seeded UUID allocator before Core import and compares in-memory, SQLite, and SQLite closed and reopened after each preparation. The mini and persistent inhibition workloads match, including their query signatures and use results. The correction workload differs at `ac-q-c03` and the source-aware workload at `sm-contested` and `sm-evidence-cap`, both with and without reopen. All compared aggregate metrics, use signatures and source-assessment observations match. The raw comparison remains failing.

The mini workload was repeated with the exact Git-installed candidate and reproduced all three sets of fingerprints from the source-checkout run. The standalone comparison harness and its integration test are maintained in the independent Bench repository.

The [support-evidence review](../review-0.19.5-support-evidence-order.md) narrows all three differences to order of the same supporting event IDs, explains the different UUID allocation paths and retains full query details. The user explicitly approved those exact three differences for this candidate; the [separate reviewed report](data/bench-0.19.5-embedded-reviewed.json) passes without altering the raw comparison. This SQLite-order approval is separate from the frozen correction above. The Bench SQLite check covers four representative workloads and reopens within one Bench process; it does not run every frozen profile against SQLite or establish fresh-process Bench adapter reconstruction. The PostgreSQL Bench check above covers source diagnostics rather than every cognitive store. Core's protocol and integration tests supply additional PostgreSQL coverage, but the complete end-to-end three-backend gate must not be claimed on the basis of these Bench runs alone.

## PostgreSQL learning cleanup defect

A [three-backend run](data/bench-0.19.5-threeway-pre-fix.json) using the complete PostgreSQL cognitive-state bundle revealed score and context-order changes on the mini workload after an earlier run. A [first](data/bench-0.19.5-pg-before-1.json) and [second](data/bench-0.19.5-pg-before-2.json) run against the same fresh PostgreSQL database reproduced the issue: the first matched in-memory and SQLite, the second did not. `PostgresLearningStore.clear()` deleted learning events but left aggregate learning states and learned associations, so `Memory.clear()` did not fully clear the tenant's cognitive state. The source fix deletes all three categories in one transaction; event deletion cascades to feedback items. A regression test covers removal, another tenant's isolation and a fresh replay.

Two exploratory mini runs with the uncommitted source fix, on a separate fresh database, [both matched](data/bench-0.19.5-pg-after-1.json) ([second run](data/bench-0.19.5-pg-after-2.json)). They record a dirty source patch and cannot use either approval issued for commit `fa9c993`. The fix requires a new identified candidate and independent reruns before the architecture can be frozen. The original three-way output and pre-fix results remain preserved.

The fix and its regression test are now committed and pushed as `f289035351e3c101fd932f4d6d9e9cd56583ace0`. The full PostgreSQL-enabled Core suite passed on Python 3.11–3.13 with 1,031 tests per runtime.
