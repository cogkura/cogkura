# Embedded stabilisation findings (0.19.6, in progress)

This is an implementation and validation record, not a release-acceptance statement. The released baseline is `v0.19.5` at `13ad7336de1e8be4eba95fbd673ccb448c612d03`; prior candidate-specific approvals apply to `f289035351e3c101fd932f4d6d9e9cd56583ace0` only. See the [design](../design-embedded-stabilisation-0.19.6.md) for required gates.

## Baseline and independent Bench

The previously uncommitted independent Bench harness, raw and reviewed comparisons and exact candidate approvals are preserved in Bench commit `5bf9969`. Bench development now pins the public Core release commit separately. Its prior approvals are not carried over. On CPython 3.12.16, the complete Bench suite passed 326 tests with PostgreSQL enabled against the Git-installed 0.19.5 release. The original raw frozen comparison on that release reports 392 matching query signatures and one changed signature (`ac-q-c20`); its fingerprint pair is the previously identified correction. PostgreSQL source diagnostics passed with 191/191 fixture checks, and diagnostics comparisons matched. The user approved this exact correction for the published commit on 16 November 2026; the original baseline and raw result remain unchanged. This does not approve a future 0.19.6 candidate.

## Runtime compatibility

[Hosted Core CI](https://github.com/cogkura/cogkura/actions/runs/43976639196) for development commit `e779402` passed all 15 Linux/macOS/Windows × Python 3.11–3.15 jobs. The separate Linux PostgreSQL 16 matrix passed 1,031 tests with zero skips on each of the five Python versions. Portable Linux/macOS jobs each passed 985 with 46 PostgreSQL-dependent skips; Windows jobs passed 984 with 47 skips, including the POSIX-only permissions test. Managed CPython versions were 3.11.18, 3.12.16, 3.13.18, 3.14.10 and 3.15.2, all linked to SQLite 3.53.1. The hosted reports identify ext2/ext3, APFS and NTFS respectively. These gates validate that development commit; an eventual 0.19.6 release candidate still needs exact-artifact validation. On macOS APFS using CPython 3.14.10, SQLite 3.53.1, WAL, foreign keys on, synchronous FULL and fullfsync on, the non-PostgreSQL Core suite passed 985 tests and skipped 46. Both CPython 3.14.10 and 3.15.2 passed the full PostgreSQL-enabled suite with clean databases and a read-only source role: 1,031 passed, no skips per version. Both used SQLite 3.53.1 with the same settings. An earlier 3.14 run failed the read-only-role test because the fixture incorrectly used a superuser; an earlier 3.15 run reused populated databases and failed two stateful tests. Both were fixture errors, corrected before the clean runs. Older Python release evidence remains documented in the [0.19.5 findings](0.19.5-embedded-architecture-freeze.md).

## Unresolved release gates

- Further published-release backend differences and future 0.19.6 benchmark exceptions require candidate-specific review; no previous approval is broadened.
- The Python 3.11 historical-gold differences need field-level explanation and deterministic evidence.
- A focused independent fresh-process SQLite restart smoke test is implemented; broader backend scenarios, full uninstrumented performance, all supported-platform gates and exact 0.19.6 candidate artifact verification remain incomplete.
- A passing release requires the complete matrix, including PostgreSQL, and separate authorisation for tagging and publication.

## Preliminary performance observation

The existing synthetic workload now has an opt-in uninstrumented mode that disables both `tracemalloc` and SQL tracing. A 100-observation, 500-revision smoke run completed with matching SQLite/in-memory logical outputs. It ran concurrently with other tests, so its timings are not a stable baseline and are not used for release acceptance. The workload also lacks the requested mix and operation coverage; those remain to be implemented.

## Cross-platform frozen gate remains open

Hosted Linux Bench CI for the public 0.19.5 release reported five unexpected query fingerprint differences in interference and inhibition workloads on Python 3.12–3.15 relative to the retained macOS baseline. Python 3.11 also differed from the macOS same-version report in those five runs. Aggregate metrics and uses match for those five runs, but fingerprint differences do not establish whether identities, ordering, scores or other details changed. They remain unapproved and block the requested release gate. Bench preserves the raw reports and now captures full query signatures for diagnosis.

The [Python 3.11 audit](https://github.com/cogkura/cogkura-bench/blob/a7b7543/docs/findings/embedded-python311-historical-audit.md) enumerates 61 numeric fields and 10 query fingerprints against original gold. All match the earlier Core's recorded macOS Python 3.11 results; one fingerprint is the separately approved correction. Follow-up query-detail captures show the other nine differ only in 52 floating-point activation and assessment fields on macOS Python 3.11 versus 3.12, with maximum absolute difference `4.44e-16`; query identities, order and other fields match. A separate Linux Python 3.12 control also produced identical complete outputs for older and released Core. These findings do not approve any tolerance or change frozen gold. Same-version results from different operating systems are not an equivalent-environment control.

A separate [small uninstrumented observation](data/0.19.6-uninstrumented-small.json) used 100 uniformly generated observations, five revisions each and 20 fixed-clock recall queries on macOS 15.8.1 x86-64/APFS, CPython 3.14.10 and SQLite 3.53.1 with fullfsync enabled. SQLite warm recall median was 923 ms and sample p95 979 ms; in-memory median was 884 ms. The process pass took 2.41 s on SQLite; each 100-observation write pass took 2.23–2.38 s. The closed database was 1,490,944 bytes. Counts, history, semantic values and ranked outputs matched in memory. These are single-machine observational timings with a synthetic uniform workload, not an interactive SLA or a statistically established regression comparison. There are no cold-start, CPU/RSS, richer correction/withdrawal, medium or large workload measurements in this sample.

## Wheel smoke infrastructure

`scripts/verify_wheel_runtime.py` verifies that Core imports from the installed distribution with the expected version and without SQLAlchemy, that SQLite migration files are present, and that recall identity and score survive reopening in a fresh process. It passed locally on CPython 3.14.10 and 3.15.2 against a wheel built from the current in-progress source, which still declares `0.19.5`. The five Linux wheel jobs in [hosted CI](https://github.com/cogkura/cogkura/actions/runs/43977989657) passed on Python 3.11–3.15 for commit `2d4f61d`. The full 15-job portability matrix and five PostgreSQL jobs also passed in that run. These are infrastructure checks, not proof of the final 0.19.6 candidate or its published artifact.

The medium synthetic run (1,000 observations, 5,000 revisions, five recalls) was stopped after more than six minutes without completing or producing a report; one process snapshot showed approximately one CPU core in use and about 96 MB RSS. It was executing retrieval feature work when interrupted. This is an incomplete exploratory run, not a throughput estimate, an operation-level latency measurement, or a supported capacity claim. The large workload was not run. A realistic mixed-workload performance harness and bounded diagnostics remain outstanding.

The extended [small synthetic sample](data/0.19.6-uninstrumented-extended-small.json) uses 20 warm queries and reports per-operation samples without tracemalloc or SQL tracing. SQLite medians/p95 were: observe 22.21/24.89 ms (500 observations/revisions), recall 1,035/1,130 ms, prepare context 1,014/1,120 ms, source assessment 2.81/4.17 ms, slot inspection 2.11/3.05 ms and recorded context use 25.91/32.36 ms. The single process pass took 2.47 s; open and reopen were single samples of 70.8 and 3.6 ms. Total process peak RSS across both backends was 43.6 MB and total CPU was 81.2 s. SQLite/in-memory counts, historical values, semantic values and pre-reinforcement recall results matched. These one-machine values are not production limits; the workload remains uniformly generated and does not cover the requested correction/withdrawal mix, cold retrieval distribution or equivalently controlled prior-release performance comparison.

The public PyPI `0.19.5` wheel was SHA256-verified against PyPI metadata (`29ec696acba22b9752948d8f394551066ad1038989e0a30244162a6ed7460fe0`). Its 76 packaged Python and SQL files are byte-identical to the current Core `src/cogkura` tree as of development commit `ececd22`. The published wheel passed the dependency-free fresh-process persistence smoke test locally on Python 3.15. This validates the 0.19.5 baseline only, not a future 0.19.6 artifact.

The subsequent [Core CI run](https://github.com/cogkura/cogkura/actions/runs/43978712994) passed all 25 jobs at development commit `ececd22`: 15 OS/Python combinations, five PostgreSQL-enabled jobs and five dependency-free wheel restart checks. The PostgreSQL jobs each passed 1,032 tests with zero skips. A later documentation-only findings update does not turn this into final 0.19.6 artifact validation.

A sequential same-machine Python 3.15.2 comparison used the [published 0.19.5 wheel](data/0.19.6-perf-pypi-0.19.5-py315.json) followed by [development source](data/0.19.6-perf-dev-source-py315.json), with the same 100/500 synthetic extended workload. SQLite recall median was 1,083 ms versus 970 ms, and context preparation median was 1,032 ms versus 1,101 ms, respectively. Both samples retained the workload's logical parity checks. These are single runs with ordinary machine variance, insufficient to rule out a performance regression or to set a target. The corresponding Core Python and SQL sources were byte-identical, as documented above.
