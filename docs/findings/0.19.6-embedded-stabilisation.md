# Embedded stabilisation findings (0.19.6, in progress)

This is an implementation and validation record, not a release-acceptance statement. The released baseline is `v0.19.5` at `13ad7336de1e8be4eba95fbd673ccb448c612d03`. The user separately approved narrowly scoped differences for this published baseline and for the earlier `f289035351e3c101fd932f4d6d9e9cd56583ace0` candidate; neither approval applies to a 0.19.6 candidate. See the [design](../design-embedded-stabilisation-0.19.6.md) for required gates.

## Baseline and independent Bench

The previously uncommitted independent Bench harness, raw and reviewed comparisons and exact candidate approvals are preserved in Bench commit `5bf9969`. Bench development now pins the public Core release commit separately. Its prior approvals are not carried over. On CPython 3.12.16, the complete Bench suite passed 326 tests with PostgreSQL enabled against the Git-installed 0.19.5 release. The original raw frozen comparison on that release reports 392 matching query signatures and one changed signature (`ac-q-c20`); its fingerprint pair is the previously identified correction. PostgreSQL source diagnostics passed with 191/191 fixture checks, and diagnostics comparisons matched. The user approved this exact correction for the published commit on 16 November 2026; the original baseline and raw result remain unchanged. This does not approve a future 0.19.6 candidate.

## Runtime compatibility

[Hosted Core CI](https://github.com/cogkura/cogkura/actions/runs/43976639196) for development commit `e779402` passed all 15 Linux/macOS/Windows × Python 3.11–3.15 jobs. The separate Linux PostgreSQL 16 matrix passed 1,031 tests with zero skips on each of the five Python versions. Portable Linux/macOS jobs each passed 985 with 46 PostgreSQL-dependent skips; Windows jobs passed 984 with 47 skips, including the POSIX-only permissions test. Managed CPython versions were 3.11.18, 3.12.16, 3.13.18, 3.14.10 and 3.15.2, all linked to SQLite 3.53.1. The hosted reports identify ext2/ext3, APFS and NTFS respectively. These gates validate that development commit; an eventual 0.19.6 release candidate still needs exact-artifact validation. On macOS APFS using CPython 3.14.10, SQLite 3.53.1, WAL, foreign keys on, synchronous FULL and fullfsync on, the non-PostgreSQL Core suite passed 985 tests and skipped 46. Both CPython 3.14.10 and 3.15.2 passed the full PostgreSQL-enabled suite with clean databases and a read-only source role: 1,031 passed, no skips per version. Both used SQLite 3.53.1 with the same settings. An earlier 3.14 run failed the read-only-role test because the fixture incorrectly used a superuser; an earlier 3.15 run reused populated databases and failed two stateful tests. Both were fixture errors, corrected before the clean runs. Older Python release evidence remains documented in the [0.19.5 findings](0.19.5-embedded-architecture-freeze.md).

A later [Core CI run](https://github.com/cogkura/cogkura/actions/runs/43980771158) for development commit `bff9d78` passed all 25 jobs; the five PostgreSQL jobs each passed 1,033 tests without skips. This is development evidence, not exact 0.19.6 artifact validation.

## Unresolved release gates

- The five-version candidate comparisons have exact, candidate-specific approvals and separate reviewed results. Any different candidate or further difference requires its own review.
- Cold-device retrieval distributions and completed medium/large scaling measurements remain incomplete. The 250-observation mixed run and the interrupted 1,000-observation run quantify and bound the currently observed limitation; they do not prove a production latency or capacity target.
- The built candidate wheel was checked locally and across the CI Python matrix; the eventual tagged source and published artifact still require verification against the validated candidate.
- Release acceptance requires final disposition of outstanding findings and separate authorisation for tagging and publication.

## Preliminary performance observation

The existing synthetic workload now has an opt-in uninstrumented mode that disables both `tracemalloc` and SQL tracing. A 100-observation, 500-revision smoke run completed with matching SQLite/in-memory logical outputs. It ran concurrently with other tests, so its timings are not a stable baseline and are not used for release acceptance. That earlier run did not include the mixed data or extended operations later measured below.

## Cross-platform frozen comparisons

Hosted Linux Bench CI for the public 0.19.5 release reported five unexpected query fingerprint differences in interference and inhibition workloads on Python 3.12–3.15 relative to the retained macOS baseline. Python 3.11 also differed from the macOS same-version report in those five runs. Follow-up signature analysis found floating-point changes, with identities, ordering and other fields unchanged. On 16 November 2026 the user approved the exact recorded Linux results for public Core commit `13ad733`: 75 fields on Python 3.11.18 and five fingerprints on each of Python 3.12.16–3.15.2. Bench commit `f41299c` records the original gold digest and exact before/after values in a fail-closed, version- and candidate-scoped review; raw failures remain available. This is not an approval for 0.19.6, nor a general numerical tolerance.

The [Python 3.11 audit](https://github.com/cogkura/cogkura-bench/blob/88bf43f/docs/findings/embedded-python311-historical-audit.md) enumerates 61 numeric fields and 10 query fingerprints against original gold. All match the earlier Core's recorded macOS Python 3.11 results; one fingerprint is the separately approved correction. Follow-up query-detail captures show the other nine differ only in 52 floating-point activation and assessment fields on macOS Python 3.11 versus 3.12, with maximum absolute difference `4.44e-16`; query identities, order and other fields match. A separate Linux Python 3.12 control also produced identical complete outputs for older and released Core. These findings do not approve any tolerance or change frozen gold. Same-version results from different operating systems are not an equivalent-environment control.

A separate [small uninstrumented observation](data/0.19.6-uninstrumented-small.json) used 100 uniformly generated observations, five revisions each and 20 fixed-clock recall queries on macOS 15.8.1 x86-64/APFS, CPython 3.14.10 and SQLite 3.53.1 with fullfsync enabled. SQLite warm recall median was 923 ms and sample p95 979 ms; in-memory median was 884 ms. The process pass took 2.41 s on SQLite; each 100-observation write pass took 2.23–2.38 s. The closed database was 1,490,944 bytes. Counts, history, semantic values and ranked outputs matched in memory. These are single-machine observational timings with a synthetic uniform workload, not an interactive SLA or a statistically established regression comparison. There are no cold-start, CPU/RSS, richer correction/withdrawal, medium or large workload measurements in this sample.

## Wheel smoke infrastructure

`scripts/verify_wheel_runtime.py` verifies that Core imports from the installed distribution with the expected version and without SQLAlchemy, that SQLite migration files are present, and that recall identity and score survive reopening in a fresh process. It passed locally on CPython 3.14.10 and 3.15.2 against a wheel built from the current in-progress source, which still declares `0.19.5`. The five Linux wheel jobs in [hosted CI](https://github.com/cogkura/cogkura/actions/runs/43977989657) passed on Python 3.11–3.15 for commit `2d4f61d`. The full 15-job portability matrix and five PostgreSQL jobs also passed in that run. These are infrastructure checks, not proof of the final 0.19.6 candidate or its published artifact.

The medium synthetic run (1,000 observations, 5,000 revisions, five recalls) was stopped after more than six minutes without completing or producing a report; one process snapshot showed approximately one CPU core in use and about 96 MB RSS. It was executing retrieval feature work when interrupted. This is an incomplete exploratory run, not a throughput estimate, an operation-level latency measurement, or a supported capacity claim. The large workload was not run. The bounded medium and large scaling investigations remain outstanding.

The extended [small synthetic sample](data/0.19.6-uninstrumented-extended-small.json) uses 20 warm queries and reports per-operation samples without tracemalloc or SQL tracing. SQLite medians/p95 were: observe 22.21/24.89 ms (500 observations/revisions), recall 1,035/1,130 ms, prepare context 1,014/1,120 ms, source assessment 2.81/4.17 ms, slot inspection 2.11/3.05 ms and recorded context use 25.91/32.36 ms. The single process pass took 2.47 s; open and reopen were single samples of 70.8 and 3.6 ms. Total process peak RSS across both backends was 43.6 MB and total CPU was 81.2 s. SQLite/in-memory counts, historical values, semantic values and pre-reinforcement recall results matched. These one-machine values are not production limits; the workload remains uniformly generated and does not cover the requested correction/withdrawal mix, cold retrieval distribution or equivalently controlled prior-release performance comparison.

The public PyPI `0.19.5` wheel was SHA256-verified against PyPI metadata (`29ec696acba22b9752948d8f394551066ad1038989e0a30244162a6ed7460fe0`). Its 76 packaged Python and SQL files are byte-identical to the current Core `src/cogkura` tree as of development commit `ececd22`. The published wheel passed the dependency-free fresh-process persistence smoke test locally on Python 3.15. This validates the 0.19.5 baseline only, not a future 0.19.6 artifact.

The subsequent [Core CI run](https://github.com/cogkura/cogkura/actions/runs/43978712994) passed all 25 jobs at development commit `ececd22`: 15 OS/Python combinations, five PostgreSQL-enabled jobs and five dependency-free wheel restart checks. The PostgreSQL jobs each passed 1,032 tests with zero skips. A later documentation-only findings update does not turn this into final 0.19.6 artifact validation.

A sequential same-machine Python 3.15.2 comparison used the [published 0.19.5 wheel](data/0.19.6-perf-pypi-0.19.5-py315.json) followed by [development source](data/0.19.6-perf-dev-source-py315.json), with the same 100/500 synthetic extended workload. SQLite recall median was 1,083 ms versus 970 ms, and context preparation median was 1,032 ms versus 1,101 ms, respectively. Both samples retained the workload's logical parity checks. These are single runs with ordinary machine variance, insufficient to rule out a performance regression or to set a target. The corresponding Core Python and SQL sources were byte-identical, as documented above.

The [mixed small sample](data/0.19.6-uninstrumented-mixed-small.json) adds three applied corrections and three withdrawals to the 100-observation/five-revision base: 106 observations, 506 observation revisions, 106 episodes and 106 semantic revisions. On the same macOS/CPython 3.14.10 setup, SQLite recall median/p95 was 895/976 ms, context preparation 963/1,092 ms, observation writes 22.08/30.03 ms, source assessment 2.78/3.70 ms, slot inspection 2.24/3.43 ms and recorded use 23.14/25.02 ms. The two processing calls had a 1.36 s median; with only two samples no p95 is reported. The SQLite/in-memory logical checks and applied-operation counts matched. This single mixed synthetic run does not establish scaling, cold-query latency, or performance equivalence at medium/large sizes.

A separate [instrumented diagnostic](data/0.19.6-instrumented-mixed-small.json) for the same small mixed dataset counted 530 SQLite statements across two recall queries and 6.25 MB peak Python-traced allocation. It used both SQL tracing and tracemalloc; its elapsed times are not the uninstrumented baseline. Row/materialisation counts, cold-query distributions and a completed larger mixed workload are still required for full performance characterisation.

## Candidate validation and scaling observation

Core commit `788444d7a4d5149ea397852cc4cb13552a7ca278` declares version `0.19.6`. The only change under `src/cogkura/` from the public 0.19.5 release is that declared version; algorithms and storage code are byte-identical. Its [hosted Core matrix](https://github.com/cogkura/cogkura/actions/runs/44147497151) passed 25 jobs: Linux, macOS and Windows on Python 3.11–3.15, five PostgreSQL-enabled suites and five isolated-wheel restart checks. The independent [Bench candidate findings](https://github.com/cogkura/cogkura-bench/blob/main/docs/findings/embedded-core-0.19.6-788444d-candidate.md) retain raw macOS and Linux reports; the user separately approved the exact correction, three support-order differences and exact Linux values for this candidate on 17 November 2026. Separate reviewed Linux comparisons passed on all five Python versions. The raw comparisons remain failed and do not change frozen gold.

The candidate wheel and sdist passed `twine check`. The wheel SHA-256 is `da408b69dde5e97ed8b7d35c860738b1a914b9fb11d8427ddf01ea550c7fb555`; all 77 packaged `cogkura/` files matched the exact candidate commit. A fresh Python 3.15 wheel installation passed the dependency-free restart smoke test. Independent Bench also ran the wheel on Python 3.12 with PostgreSQL: frozen runs matched the Git-installed candidate exactly and source diagnostics passed. Its source retrieval latency differed, as expected for a timing measurement. The separately computed sdist SHA-256 was `681e04aa317923c13911997e4d827e2894122cb0e2b12b0228d75b8118157b07`. These are local build artifacts, not a published package; final release artifact verification remains required.

An additional [mixed scaling observation](data/0.19.6-uninstrumented-mixed-250.json) used 250 observations with five revisions each, then three corrections and three withdrawals, on macOS 15.8.1/APFS, CPython 3.14.10 and SQLite 3.53.1. Five SQLite recall samples had a 5.32 s median; five context-preparation samples had a 5.33 s median. In-memory recall median was 5.10 s. Observation write median/p95 was 22.95/24.95 ms; other per-operation sample counts and database/WAL sizes are in the report. Logical parity checks passed. The process used 109.34 CPU seconds and peaked at 58.4 MB RSS across both backends. Other validation tasks ran concurrently, and five recall samples are insufficient for p95; these figures characterize this one run, not a release threshold. Together with the earlier 100-observation sample they indicate steep scaling in this synthetic workload, but do not establish a controlled regression against 0.19.5. The 1,000-observation run was stopped after six minutes and the 10,000-observation run was not attempted; neither is a supported-capacity claim. Profiling and retrieval redesign require a separate proposal rather than changing frozen algorithms here.

A separate [reopen measurement](data/0.19.6-reopen-perf.json), reproducible with `PYTHONPATH=.:src python docs/findings/data/0.19.6-reopen-perf.py`, used the mixed 100-observation/five-revision dataset on the same host. Reopening took 5.70 ms, the first recall after reopening took 935.73 ms, and five subsequent identical recalls took 906.56–1,045.16 ms; the retrieved outputs were identical. This is one reopened-owner sample within the same process: the operating-system page cache was not cleared, so it does not measure a cold-device or cold-process distribution. The 20-query warm sample above remains the more useful warm-latency observation.

A [fresh-process sample](data/0.19.6-cold-process-perf.json) on the same 100-observation mixed dataset used a new Python process after the writer closed. The first recall took 1,148.30 ms after a 5.55 ms database open; five repeated recalls took 910.32–988.67 ms, with identical output. The [measurement script](data/0.19.6-cold-process-perf.py) can be run with `PYTHONPATH=.:src python docs/findings/data/0.19.6-cold-process-perf.py`. This is one fresh-process sample with the OS page cache retained; it is not a cold-device distribution or a production target.
