## Answerability and selective consumption

A non-empty rendered `MemoryContext` is not proof that a query is answerable.
The caller must inspect `context.assessment.flags`: when `MISSING_KNOWLEDGE` is
present it should communicate the missing evidence rather than treating the
rendered context as a sufficient answer. In the new regression, an unrelated
astronomy episode is selected and rendered for a structured production-database
question while the assessment retains `MISSING_KNOWLEDGE`; memory and SQLite
produce the same result. The assessment is also unchanged by repeated preparation
and agrees with the independent assessment API for that fixture.

`record_context_use(context)` records **all** selected `context.recall_results`.
When only some selected memories were actually consumed, pass just those
`RecallResult` objects to the existing `record_access()` public API instead.
Do not record an unrelated item merely because it was returned. Application
answerability, fallback and selective-use decisions belong to the Agent.

## Project scope

Pass the known project `subject_id` for project-specific questions. The existing
0.20.2 top-ten regression covers incident and migration evidence for the scoped
fixture. Omitting `subject_id` performs tenant-wide retrieval; a project name in
the query is not automatic subject resolution. The earlier unscoped fixture
placed the incident and migration evidence at ranks 26 and 27. Agent-side
project identity resolution is responsible for selecting the subject.

Processing scope and the remaining cross-subject questions are tracked in
[scoped processing](0.20.3-scoped-processing.md). The release owner accepted
the measured initial-Agent envelope and deferred history compaction; see the
[SQLite scaling investigation](0.20.3-scoped-read-scaling.md).
