# 0.18.0 source provenance findings

**Decision:** ship source provenance as a separate, read-only operation after context preparation.

The existing observation revision store already snapshots the attributes required for historical attribution: source version, retained metadata, and observation time. The implementation therefore adds batch revision resolution to both in-memory and PostgreSQL stores without a schema migration.

The resolver deliberately reports only source identity and an optional `source_ref`; it does not expose stored content, arbitrary metadata, source type as a historical value, or connector behaviour. It distinguishes an unavailable source observation, an unavailable revision, and a missing locator.

Observed limits:

- `source_ref` is application-supplied metadata; Core never infers it from memory text.
- A semantic evidence relation is reported only where an existing derivation maps the exact observation revision to SUPPORTS or CONTRADICTS.
- Revision currency says only whether the referenced revision is the latest known row. It does not establish factual currentness or authority.
- Output is bounded by `max_evidence`; the total evidence count and truncation status remain visible.

The resulting API is the evidence boundary for later authority and correction work, but it does not promote single-source claims, adjust ranking, or reinterpret `valid_at` and `as_of`.
