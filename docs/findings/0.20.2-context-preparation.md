# 0.20.2 context preparation measurements

**Status: exploratory; target and release gate remain open.**

The first measurements use the existing mixed fixture at 100 base observations,
five revisions and six corrections/withdrawals. The 0.20.1 Core source matches
`4c53eb6`; the checkout is `a62196b`. The context harness SHA-256 is
`3ed308bb51bdf8389fa70dcf6f1f3da7128f467ca5fc2a104e133d2b7cd0c620` and
its unchanged fixture script SHA-256 is
`641b007883b6ba1dfd78255a399854d09e35c63da84829be4e6a0ef8d2a32354`.
Both measurements used CPython 3.11.15, fixed evaluation time, a narrow query,
structured goal and context, a prior working-memory snapshot, pool size 50,
2,048-token budget, learning enabled, and ten repetitions per operation.

| Complete operation | Memory median (ms) | SQLite median (ms) |
| --- | ---: | ---: |
| recall | 95.13 | 135.64 |
| prepare_context | 130.21 | 167.22 |
| select_working_memory | 123.57 | 162.99 |
| assess_memory | 102.62 | 143.84 |
| record_context_use | 0.05 | 22.63 |

Raw samples and settings are in `data/0.20.2-context-{memory,sqlite}-100.json`.
The repeated contexts were equal with the state and evaluation time held fixed.
The two backends also produced the same rendered-context hash and fixture counts;
this does not compare all diagnostics or cognitive state.
Each measured use was recorded after all reads and changes state, so the use
samples are not independent repeated measurements on an unchanged fixture.
Timings are whole operations and should not be added together. The 10 samples
are exploratory and do not establish p95 or a performance target.

Additional combinations of query shapes, pools, budgets and learning state,
independent processes, full output validation and broader cross-backend
comparisons remain to be run.
No Agent-facing target is proposed from this small sample.

A second exploratory scenario used 250 observations, a broad query, pool size
20, a 256-token budget, learning disabled, and no structured context or prior
snapshot. For memory/SQLite respectively, median times in milliseconds were:
recall 202.61/298.73, prepare 214.82/314.19, selection 208.33/307.80,
assessment 205.11/299.30, and recorded use 0.05/22.28. Each backend produced
equal repeated contexts; rendered hashes matched. Raw reports are
`data/0.20.2-context-{memory,sqlite}-250-broad.json`. As above, use samples
mutate state, and these measurements do not establish a target.

At 1,000 observations, an exploratory run used an unrelated query,
pool size 100, 512-token budget and structured context. Median recall,
preparation, selection and assessment were 757.48, 974.39, 964.27 and 916.65 ms;
recorded use was 0.05 ms. The repeated contexts matched. The permissive
benchmark threshold still selected eight memories, so this run alone does not
validate relevance or missing-knowledge correctness. Raw observations are in
`data/0.20.2-context-memory-1000-irrelevant.json`. SQLite medians for the
same operations were 1,161.87, 1,354.00, 1,350.58, 1,304.39 and 22.06 ms
respectively. Its repeated contexts matched and its rendered hash matched the
memory report; raw observations are in
`data/0.20.2-context-sqlite-1000-irrelevant.json`. Representative correctness
checks remain open.

## Narrow-query budget evidence and proposal

With the in-progress 0.20.2 working source, 1,000 observations, a narrow
query, structured goal/context, a previous snapshot, pool size 50, a 2,048-token
budget and learning enabled, 20 fixed-state preparations had these whole-call
latencies:

| Backend | Median | Nearest-rank p95 |
| --- | ---: | ---: |
| Memory | 1.359 s | 1.532 s |
| SQLite | 1.844 s | 1.910 s |

Repeated contexts and rendered hashes matched across the two runs. The previous
snapshot is prepared before timing, so these are warm measurements; each p95
includes the first of the 20 timed preparations. Raw samples and the other
operation timings are in `data/0.20.2-context-{memory,sqlite}-1000-narrow.json`.
This is one process per backend and does not establish repeatability or a
production SLA.

**Proposed for review, not approved or yet demonstrated:** for this specific
1,000-observation fixture and configuration on the agreed reference host, set a
warm `prepare_context()` nearest-rank p95 target below **2.5 seconds** separately
for memory and SQLite. Use at least 100 fixed-state preparations including the
first timed preparation, in each of three independent processes. The proposal
provides roughly 31% headroom above the observed 1.910-second SQLite p95; the
choice is provisional because that observation has only 20 samples in one
process. Preserve all samples and investigate failed runs under the same
invalid-run policy as the recall benchmark. This target is fixture-specific,
does not cover all budgets or queries, and requires explicit review and approval
before the 0.20.3 freeze.

## Independent preparation runs

On the user-confirmed reference Mac, a preparation-only mode now measures
100 fixed-state preparations per independent process with the proposed narrow
configuration. It does not interleave recall, selection, assessment or recorded
use between samples. The prior snapshot is prepared before timing. Source and
fixture hashes, process ID, host load, all samples, context equality and a
rendered hash are retained in each report.

Three memory processes produced p95s of 1.354, 1.359 and 1.324 seconds;
medians were 1.271, 1.260 and 1.252 seconds. Three SQLite processes produced
p95s of 1.843, 1.796 and 1.812 seconds; medians were 1.736, 1.731 and 1.729
seconds. The six process IDs were distinct and their recorded source and
environment identities matched. Repeated contexts were equal within each
process and their rendered hashes matched across both backends. Individual
reports are `data/0.20.2-context-repeat-{memory,sqlite}-1000-run{1,2,3}.json`.

Each measurement is below the proposed 2.5-second fixture-specific target, but
the target is still not approved. Equality of rendered contexts and selected
counts does not verify every diagnostic or the full variation matrix.

## Mixed-fixture output regression

A separate 100-observation mixed-fixture regression checks memory and SQLite
with learning both enabled and disabled. For a subject-scoped relevant query
and an unresolved slot query, it varies budget, structured context and a
previous snapshot. It asserts repeated full-context equality, prompt-budget
limits, agreement with standalone assessment, expected deployment evidence,
and the missing-knowledge flag for the unresolved slot. Rendered contexts,
ranked statements and scores, assessment flags and signals, and selected
counts match across the two backends. It uses the permissive fixture threshold,
so an unresolved query can still retrieve unrelated memories; the assertion is
about the missing-knowledge flag, not an absence of results. This improves
specific correctness coverage but does not complete the variation matrix or
establish all diagnostic behavior.
The regression passed against Core `64f85f78acd2046cafe0212c84b45c1d221affd4`
installed from the official Git origin on CPython 3.11.15.

The same output assertions were run with the official candidate at 250 and
1,000 observations, using learning enabled and a candidate pool of 20. At both
sizes, memory and SQLite matched on the recorded rendered context, ranked
items and scores, flags, signals and counts for two relevant query configurations
and the unresolved slot. Relevant evidence was present, budget limits and
repeated-context equality held, standalone assessments agreed, and the
unresolved slot reported missing knowledge. These are correctness probes, not
latency measurements. The reproducible driver is `scripts/check_context_outputs.py`;
reports are `data/0.20.2-context-output-{250,1000}.json`. This does not cover
every query, learning state or diagnostic at these sizes.

A separate unrelated-population check inserts 20 astronomy observations and
asks for an unrelated production-database slot with default activation settings.
Memory and SQLite both set `MISSING_KNOWLEDGE`, returned the same assessment
flags and signals, and repeated contexts were identical. They did not fabricate
a database statement. In exploratory runs each nevertheless selected and
rendered one unrelated planet observation. The missing-knowledge flag therefore
does not imply an empty rendered context; Agent integration should inspect the
assessment rather than assume every rendered item answers the question. This
is a focused fixture, not a general relevance or production-latency guarantee.

The user recommends treating `MISSING_KNOWLEDGE` as an explicit answerability
warning even when Core renders memories. This does not require suppressing the
rendered context or changing Core ranking. The current experimental Agent
0.1.0 includes assessment flags in its response but calculates `insufficient`
only from whether items or rendered text are empty; implementing and validating
the answerability warning in Agent remains follow-up work, rather than a claim
that the present Agent already enforces it.
