# 0.20.x release gate status

This is a status and review record, not a release approval. The implementation is an uncommitted candidate based on Core `9745201bfcc5410d678a07737a4c935dd294e5b4`. The retained [combined implementation patch](data/0.20.0-combined-candidate-source.patch) has SHA-256 `31d6f90fdc7a661b44c0e5fca4f1936ed098d852c7bef62093332d2b58179257`. A patch hash supports these exploratory comparisons but is not the clean commit and installed distribution identity required by the release reviewers.

## Source transition decision and frozen results

The intended source inspection reports both an earlier correction and a later withdrawal, once each is known. The independent Bench `source_aware_metamemory_v1` fixture contains exactly such a correction (`sm-chain-replace`) and withdrawal (`sm-chain-withdraw`), but its `sm-withdrawn` expectation contains only the latter. The candidate reports both, as selected by the user. The original fixture remains unchanged: its source-check result is 190/191, so the existing strict reviewer still fails. Backend parity with that result is not a passing source-accuracy result.

The Core regression `test_closed_correction_knowledge_survives_withdrawal_across_backends` now also checks both relations, their predecessor and successor linkage, effective and knowledge times, distinct asserting evidence, and that later transitions are not exposed at earlier knowledge times. The focused run passed in memory, SQLite, and a disposable local PostgreSQL instance (3 passed).

The history fix also changes exact frozen results for `ac-q-c17`, `ac-q-hist-at-withdraw`, and `ac-q-hist-before-withdraw`, including activation and score values and a historical relation. The [exact field-level comparison](data/0.20.0-historyfix-exact-differences.json) records 19 changed fields across those three queries relative to the preceding candidate. This comparison does not by itself establish acceptance against the original frozen baseline. The previously reviewed `ac-q-c20` correction and backend supporting-event ordering differences also need candidate-specific verification; old approvals do not transfer. See the [history investigation](0.20.0-history-correction-investigation.md) and [combined candidate evidence](0.20.0-admission-lookup.md).

Bench now has a separate `source_aware_metamemory_v2` fixture and an explicit opt-in review path for the selected transition behavior. Exploratory tests report 191/191 on v2 and PostgreSQL source parity, while retaining v1's 190/191; see the [Bench findings](../../../cogkura-bench/docs/findings/source-history-v2.md). The default reviewer still requires v1. The opt-in does not approve scoring changes or establish a clean candidate identity.

To close the full gate, pin a clean release candidate and re-run independent Bench against the original frozen gold and all required backend modes, including the v2 opt-in. Review the complete exact differences for that candidate, including scoring and ordering, separately from the decision to report both source transitions. Do not silently relax the check, overwrite gold, or reuse an earlier candidate's approvals.
