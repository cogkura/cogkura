# Embedded reliability and performance findings (0.19.4)

## Recovery, migration and backups

`tests/test_sqlite_reliability.py` exercises abrupt process exit during an observation revision write, semantic reconciliation and a learning plan. Each reopens with SQLite integrity and foreign-key checks; the partial store operation is rolled back, and the semantic and learning operations can be retried. A separate child exits after committed observation and episode writes without closing; those writes survive reopening. These tests simulate process termination, not power loss or storage hardware failure. Earlier stages of `Memory.process()` may have committed before a failed reconciliation.

The online-backup test runs SQLite's backup API alongside an active writer and reopens the copy. It verifies observations, episode identities, semantic claims and revisions, learning state and connector checkpoints, plus SQLite integrity and foreign keys. It is a point-in-time backup, not a transaction spanning later writes. The upgrade suite opens databases at each earlier SQLite schema version and checks preserved observations, checkpoints, episodes, semantic history and learning state where present. Contention tests cover busy timeout, readers while a writer is active, and successful progress after lock release. A POSIX subprocess checks database and sidecar permissions under a restrictive umask; other OS and filesystem behavior is not established by that test.

## Workload and read amplification

Run `uv run python scripts/run_sqlite_workload.py --observations 80 --revisions 5 --recalls 4`. The workload uses synthetic observations, one authoritative semantic claim per subject, four fixed-clock recall queries and Python `tracemalloc`. It compares counts, exact observation history, semantic values, ranked recall statements and scores against in-memory Core. Traced timings include instrumentation overhead and are not production latency guarantees. Peak values are Python-traced allocations, not total RSS. The p95 from four calls is the slowest observed call, not a statistically reliable tail estimate.

The preserved [original baseline](data/sqlite-workload-0.19.4.json) measured 80 observations, 400 observation revisions, 80 episodes and 80 semantic revisions. Four SQLite recalls executed **5,912 SQL statements** and had a 4,447 ms median under tracing. The initial baseline compared recall results as an unordered logical set; it did not establish ranking parity.

Batching semantic child-row reads changed no cognitive algorithm and reduced the same workload to **840 statements** in the preserved [batched comparison](data/sqlite-workload-0.19.4-batched.json), an 85.8% reduction. Median traced recall was 4,456 ms, so this run does **not** establish a latency improvement. The [ranked comparison](data/sqlite-workload-0.19.4-ranked.json) retains both backends' ranked outputs, historical and semantic digests and matching parity flags. No benchmark outputs were changed to accept a discrepancy.

The [history run](data/sqlite-workload-0.19.4-history.json) covered 160 observations, 1,600 observation revisions, 160 episodes and 160 semantic revisions. Its single SQLite recall executed 370 SQL statements and took 16.6 seconds under tracing; a single observation is not a reliable latency distribution. Peak Python-traced SQLite allocations were about 11.4 MB. The main database after clean close was about 2.83 MB; the live database, WAL and shared-memory files were measured separately in the artifact. SQLite and in-memory counts, exact revision attribution, semantic values and the then-unordered logical recall results matched. Results reflect this one local machine and workload, not supported population limits.

The batching removes per-memory semantic child queries from a full inventory hydration, but semantic operations still materialize each tenant's inventory. Episode loads and some cognitive-state reads still amplify queries or scan tenant-scoped records, and the in-memory cognitive algorithms also dominate the traced workload. Large-scale workloads, cross-platform filesystems, power-failure behavior, PostgreSQL storage performance comparison and independent Bench validation remain outside the evidence above. The architecture is not frozen by this milestone.

## Validation

The full Core suite, with PostgreSQL 16 source and memory fixtures enabled, passed on Python 3.11, 3.12 and 3.13: **1,014 tests on each runtime, no skips**. A subsequently added workload-script regression ran in the focused reliability suite on all three runtimes (13 passed each). Ruff, formatting and mypy passed on all three. The existing provenance-freeze suite continues to execute SQLite, PostgreSQL and in-memory cases. Independent CogkuraBench validation remains a 0.19.5 requirement.
