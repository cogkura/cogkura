# Shared historical reconstruction: local validation

Status: local implementation and diagnostic evidence, not a release approval.
The exact Core code candidate is `4c53eb6a5f77cb9c275c7b39529f08fac7e809b1`.
The [design note](0.20.1-historical-reconstruction-design.md) records remaining
coverage limits, including legacy and custom stores and concurrent writes.

Core's full suite passed 1,081 tests with six skipped against a fresh local
PostgreSQL database. Ruff, formatting and mypy passed. Regression coverage
includes competing claims with shared mixed-time episodes, unavailable linked
snapshots, correction and withdrawal, a return to an earlier claim with multiple
revisions, explicit factual time, and parity across in-memory, SQLite and
PostgreSQL. SQLite snapshots now preserve persisted derivation ordering, and
PostgreSQL loads current derivations from the current revision only.

Bench `7373d5ff2d00b10a9dd260e5fc3869b031850c34` ran on the selected 2018
Mac, CPython 3.11.15, SQLite 3.53.1, seed 183 and `PYTHONHASHSEED=0`.
The v2 source-history fixture passed 191/191 on memory and PostgreSQL;
PostgreSQL source parity and diagnostic parity passed. Its legacy v1 fixture
still scores 190/191, because it expects only the withdrawal transition. The
strict frozen gate failed. A complete local comparison against `cf82d58` found
no changes in query fingerprints, metrics or use signatures. Consequently the
three previously documented, unapproved differences from the paired local
`b30433c` reference remain; this comparison does not approve them. Core was
loaded from a local checkout, and distribution metadata does not establish an
official Git-installed candidate. Official-origin and hosted-CI checks remain.
