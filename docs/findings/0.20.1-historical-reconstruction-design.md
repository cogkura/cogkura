# Historical reconstruction and the 0.20.1 frozen gate

Status: implementation design, not a release approval or evidence that historical
reconstruction is complete. The existing fail-closed behavior remains in effect.

The shared snapshot codec round-trips the current stored episode and semantic
memory models. Episode snapshots are now recorded by the in-memory, SQLite and
PostgreSQL stores, in the same transaction as persistent episode changes.
Recall and inspection use them for active mixed-time episodes with no semantic
derivations. Semantic-memory snapshots are also recorded transactionally by the
three stores. Recall and inspection can restore a same-revision reinforced
semantic aggregate when its earlier supporting episodes and sole revision are
known, unchanged and safe at the requested time. Competing slot revisions,
corrections, withdrawals and missing or backdated snapshots stay on the existing
path; semantic revision and relation history are not yet versioned. Episodes connected
to semantics and currently inactive episodes are not reconstructed. This is a
partial implementation, not a complete history.

Episode versions use the caller's cognitive write time; equal timestamps choose
the last write. Any backdated write makes that episode's entire version sequence
unavailable for historical projection. A database upgraded from an older schema
does not acquire earlier snapshots. Unsupported or corrupt snapshots are
unavailable rather than being reconstructed from current rows. In particular,
the codec rejects metadata that would change type in JSON, such as tuples; the
write still succeeds but records an unavailable snapshot. Snapshot content is
derived from the already retained observation data. Tenant `clear` removes
episode history along with the episode rows.

## Storage contract

Historical recall needs the actual derived state that existed at the cognitive
time being queried. The current episode row is overwritten, including its
evidence and entities. Semantic revisions have snapshots, but a later
reconciliation can update an existing revision key and overwrite that snapshot.
Observation revisions do not retain every input field used by the encoder, and
retention can remove content. Neither clipping future evidence nor re-encoding
current rows can generally recover the earlier derived state.

Add append-only, tenant-scoped versions of episodes and semantic memories for
the in-memory, SQLite and PostgreSQL stores. Each version needs the complete
stored state required by recall, including evidence, entities, context,
derivations, status and stable memory identity. Store the cognitive write time
and a deterministic tie-breaker, and atomically record versions with upserts,
deactivation and semantic reconciliation. Preserve correction and withdrawal
relations and their separate knowledge and validity times. Clear must remove the
versions for the specified tenant. Historical reads must select a coherent
version as of the requested cognitive time before constructing support indexes,
filtering candidates or calculating IDF; factual `valid_at` remains independent.

The implementation must define and test out-of-order writes and equal-time
writes explicitly. A timestamp supplied to a later processing call cannot by
itself prove what the system knew at that earlier time. Existing databases have
no complete version history: a migration may record the current state, but must
not present it as an earlier snapshot. Where coverage is unavailable, retain
fail-closed behavior and expose the limitation accurately. Custom storage
implementations need a documented compatibility path; their current protocol
does not promise versioned reads. Any snapshot retention policy must respect the
existing observation retention contract rather than silently preserving content
that the configured policy intended to discard.

Verification must cover both recall and inspection, before and after later
episode additions, same-key semantic reinforcement, correction and withdrawal,
updates, deletion and restoration, out-of-order and equal-time writes, explicit
factual time, missing history, tenant isolation, restart and migration on SQLite
and PostgreSQL, and parity with in-memory storage. It must also measure retrieval
and write overhead against the agreed 2018 Mac targets. Historical snapshots do
not retroactively reconstruct earlier data that was never stored.

## Frozen comparison

The three documented frozen query differences have two distinct causes. The
candidate removes a superseded episode from the eligible IDF population, changing
scores, and preserves a correction relation that the reference lost. Restoring
the old weights with the stale population would allow ineligible content to
influence scores; suppressing the relation would contradict the selected source
history. Those are not established correctness fixes. The exact evidence and
counterfactual are retained in Bench's
`docs/findings/core-0201-d5c009f-further-investigation.md`.

The current frozen differences remain unapproved. A reconstruction change must
be evaluated as a new exact candidate against the preserved reference, including
the complete field-level report, backend parity, source history, platform
controls and performance. Do not update the frozen baseline, relax comparisons
or transfer an approval from a different candidate. If the remaining differences
are intentional, their exact candidate-specific disposition remains a release
decision.
