# 0.20.3 scoped-processing investigation

**Status: in progress; the full cross-backend contract is not yet validated.**

The 0.20.2 project lifecycle tests cover scoped correction, withdrawal,
historical retrieval and provenance on memory, SQLite and PostgreSQL. A focused
SQLite test checks that an unrelated subject's episode, semantic and revision
history are unchanged by one scoped update. These tests do not establish the
contract for shared cross-subject evidence or every possible processing sequence.

A 0.20.3 SQLite regression processes two independent subjects with one
explicitly authoritative semantic fact each, then reprocesses the first subject
one day later without new observations. It observes no additional episode
snapshot, but one additional semantic-memory snapshot and one additional
semantic-revision snapshot. Comparing the complete stored snapshots shows that
only `updated_at` changed in each; this is explained timestamp churn, not an
additional claim or supporting observation. The second subject's snapshot rows
remain unchanged. This result identifies storage amplification even for an
unchanged selected subject; it does not show a cognitive-state change beyond the
timestamp, establish a growth rate, or imply that suppressing timestamps is
safe for historical reconstruction. Repeated and cross-backend cases remain to
be investigated before deciding whether an implementation change is required.

With the default two-episode promotion threshold, a separate regression gives
one supporting episode for the same shared-entity claim to each of two projects.
Processing both projects separately produces no semantic claim; subsequent
tenant-wide processing consolidates one claim with two supports. This passes on
memory, SQLite and a disposable local PostgreSQL instance. A single-subject call cannot aggregate those cross-subject
supports. This demonstrates one concrete case where broader processing is
required; it does not determine how all shared relationships, corrections or
withdrawals should be scheduled.

Callers should track affected subjects and avoid scheduling redundant processing.
When an update affects multiple subjects or shared evidence, a single-subject
call must not be assumed to update all dependencies. The exact supported
cross-subject boundary remains an open investigation, not a blanket guarantee.

## Expanded unaffected-subject audit

For the 12,500-observation SQLite fixture, the two semantic-inventory, two
revision-depth, two shared-relationship and two supporting-evidence variants
in the [scaling findings](0.20.3-scoped-read-scaling.md) each started from the
same baseline and altered project 049. The reproducible
`scripts/audit_unaffected_subject_history.py` compares every original row in the
three history tables with the corresponding baseline prefix and attributes
new rows by joining to current subject identity. Across all eight variants,
the original rows were preserved, every new row matched a subject, and all new
rows belonged to project 049. The shared-relationship variants only observed
new edges and did not call scoped processing. Counts are retained in the
[raw audit](data/0.20.3-unaffected-history-audits.json).

This covers the listed fixture changes and attribution through current records;
it is not proof for arbitrary shared-entity updates, deletion patterns, or every
backend. The 20-correction case also exposed substantial timestamp-only history
growth for the affected subject. That growth and its temporal implications are
tracked in the [amplification investigation](0.20.3-history-amplification.md)
and were accepted for the measured initial-Agent envelope; compaction is
deferred to a later Core version.
