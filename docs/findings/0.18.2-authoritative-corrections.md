# 0.18.2 authoritative corrections findings

**Decision:** an explicitly enabled, source-verified declaration may replace or withdraw one named semantic revision. Recurrence and 0.18.1 admission stay in place when that declaration is absent or the feature is off.

What the Core tests cover:

- One authorised correction makes the new value current and closes the predecessor at `effective_at`.
- `list_semantic_memories(valid_at=...)`, `recall`, and `prepare_context` return the predecessor before the boundary and the successor at and after it. A time before the original fact returns no semantic value.
- A recall `as_of` earlier than the correction observation does not surface the successor.
- With `SemanticCorrectionConfig(enabled=False)`, the competing authority claim stays deferred and the current value is unchanged.
- A correction without `application_asserted`, an unknown predecessor, and two incompatible corrections of the same predecessor do not choose a winner.
- Replay does not add a second successor revision.
- An explicit withdrawal leaves no current semantic answer and still returns the earlier value before `effective_at`. Processing that withdrawal three times keeps the slot withdrawn.
- `recall(as_of=...)` before a withdrawal still returns the decision known then, including its original evidence. `valid_at` at or after the withdrawal returns no authoritative value. The retracted revision stays on `list_semantic_revisions()`.
- A correction observed before its `effective_at` stays pending: the predecessor remains the current decision until that time.
- A replacement and a withdrawal of the same predecessor in one pass both defer.
- The retracted snapshot records the withdrawal's authorising observation separately from the historical fact's evidence.
- Correcting one assertion in a multi-fact episode leaves the other assertion retrievable.
- A recurrence-qualified replacement and an explicit correction of the same predecessor in one batch do not both become current.
- After withdrawal, a current-state `recall` and `prepare_context().render()` do not present the withdrawn decision. Another fact in that episode remains retrievable.
- Explicitly admitting the same assertion again after withdrawal does not restore it. 0.18.2 defers that readmission and does not select a new current revision.
- Editing the source without a withdrawal declaration does not retract the fact.
- Processing again after a correction does not restore the superseded value.
- A predecessor and its correction can be applied in one `process()` when the predecessor revision key is the one that consolidation assigns.
- The historical row's observation evidence is disjoint from the successor's evidence.
- Ordinary two-episode recurrence still promotes with `support_count=2` and no correction counter.

How history is stored:

- Migration `011_semantic_revision_snapshots.sql` adds `snapshot` JSONB on `semantic_claim_revisions`, allows status `retracted`, and allows relation `retracts`.
- New revisions write `semantic-revision-snapshot-v1`. `valid_at` reads use it. Legacy empty snapshots still overlay the current memory row.
- In-memory and PostgreSQL use the same snapshot contract. The PostgreSQL comparison, including withdrawal replay, skips unless `COGKURA_POSTGRES_MEMORY_URL` is set.

Limitations:

- Retrospective `effective_at` earlier than the asserting observation is rejected.
- A correction is refused when the slot has more than one current cardinality-one revision, even if one of them is named.
- CogkuraBench `0.3.9` was not rerun from this repository. Bench `0.3.10` should add adoption, replacement, withdrawal, temporal boundaries, stale-memory suppression, and replay without retuning retrieval or rebasing existing recall, interference, or inhibition fixtures.
- `MemoryContext.render()` does not describe the correction. Callers use revision snapshots, `list_semantic_revisions()`, and `resolve_provenance()`.
