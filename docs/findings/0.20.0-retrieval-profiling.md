# 0.20.0 retrieval profiling: initial investigation

This is preliminary evidence, not completion of the 0.20.0 release gate. The unchanged Core source was at `9745201bfcc5410d678a07737a4c935dd294e5b4` (0.19.6); only the external profiling script and documentation were added. Previous [0.19.6 results](0.19.6-embedded-stabilisation.md) remain unchanged.

## Method and observations

The new `scripts/profile_retrieval.py` uses the existing `run_sqlite_workload.py` fixture unchanged, with its fixed clock, query and correction/withdrawal configuration. For these initial measurements, each invocation constructed a fresh in-memory fixture and profiled one recall with `cProfile`. It does not instrument Core in ordinary use. Profiling changes execution cost, so these are diagnostic timings, not latency estimates or a comparison with earlier uninstrumented results. Each case is a single fresh process on macOS 15.8.1 x86-64, CPython 3.11.15, SQLite 3.53.1; normal OS caches and other host activity were not controlled. Reports retain counts, results and function-level data.

| Base observations / revisions each | Actual episodes / semantic revisions | Profiled recall wall / CPU | `_associative_entity_fit` inclusive | `_episode_association_features` calls | `canonical_content_features` calls |
| --- | --- | --- | --- | --- | --- |
| [25 / 5](data/0.20.0-profile-mixed-25-r5.json) | 31 / 31 | 0.175 / 0.174 s | 0.120 s | 2,750 | 3,497 |
| [100 / 5](data/0.20.0-profile-mixed-100-r5.json) | 106 / 106 | 2.417 / 2.344 s | 2.090 s | 48,500 | 51,572 |
| [100 / 1](data/0.20.0-profile-mixed-100-r1.json) | 106 / 106 | 2.370 / 2.353 s | 2.080 s | 48,500 | 51,572 |

The six added observations are corrections and withdrawals. At 100 / 5, `_associative_entity_fit` was called 97 times and accounted for about 86% of profiled wall time inclusively; `_episode_association_features` accounted for 1.658 s inclusive, largely nested inside that path. Inclusive times overlap and must not be added. The repeated feature calls were identical between the two revision-depth samples; this does not establish that revision history is inexpensive for other datasets or historical queries. CPU and wall timings suggest CPU-bound work for these specific in-memory runs, not zero storage cost elsewhere.

## Code analysis and proposal

For each semantic candidate, `_associative_entity_fit` traverses the seed episodes and, with semantic evidence linking enabled, scans the episode inventory for each seed. It rebuilds canonical association features for each episode during each scan, then calculates overlap and sorts related candidates before applying the configured neighbour bound. With S relevant semantic candidates, K seeds and N episodes, this portion performs up to O(S × K × N) episode-feature constructions and comparisons, plus sorting of matches. K is bounded by configuration, but the exact bound and workload determine observed growth; the two measured population points alone do not establish an empirical complexity class. The 100-observation sample made 97 semantic-fit calls and 48,500 episode-feature calls. Other paths may dominate with different configurations, relationships or historical data.

A candidate for a later optimisation is a retrieval-scoped immutable cache of episode association features and reusable seed/episode overlap results. It must retain the same full episode inventory, query-specific overlap rules, ordering, neighbour limits, paths, scores and all temporal and tenant boundaries. No pruning or persistent cache is implied. Measure each change independently and compare exact outputs and independent Bench fingerprints before acceptance. Do not infer that these profiles validate an implementation.

## Reproduction and outstanding work

From the Core checkout, run `uv run python scripts/profile_retrieval.py --observations 100 --revisions 5 --recalls 1 --output profile.json`; use separate fresh invocations for other sizes. The initial runs profile in-memory recall and record process CPU alongside wall time; cProfile's inclusive times overlap. Later backend and uninstrumented options are described below. The existing `scripts/run_sqlite_workload.py --mixed --uninstrumented` remains the longitudinal SQLite/in-memory workload. The script does not yet provide per-stage instrumentation, allocation or SQL read volumes, PostgreSQL, cold-device control, realistic project fixtures, or independent Bench validation. It uses the existing workload's rounded logical outputs, not the strict frozen Bench fingerprints.

Repeat controlled, uninstrumented multi-sample runs and add representative workload dimensions, SQLite/PostgreSQL comparisons, stage and allocation measurements, and independent validation before establishing a root-cause conclusion for the general workload or ratifying targets. The proposed performance targets remain unratified. No cognitive or storage implementation has been changed.

## Follow-up: backend, population and observation revisions

Additional cases ran sequentially on the same host and Python version, each in a fresh process. The fixture creates the stores and ingests the data before measurement, so its first recall is a first query in a warm process, not a cold-device measurement. The other system and filesystem caches were not controlled. These runs are single-process observations, not controlled host acceptance tests.

* [250 base observations, five revisions, in-memory profile](data/0.20.0-profile-mixed-250-r5.json): 256 episodes and 256 semantic revisions; one profiled recall took 14.328 s wall / 14.223 s process CPU. `_associative_entity_fit` accounted for 13.248 s inclusive (92% of wall); the declarative ranking function accounted for 14.262 s inclusive. These overlap and cannot be summed. It made 247 associative calls, 308,750 episode-feature calls and 316,472 canonical-content-feature calls. For comparison, 100 / 5 made 48,500 episode-feature calls. Increasing base population by 2.5 multiplied these calls by about 6.37, consistent with the nested-loop analysis, but not by itself proof of general scaling.
* [100 / 5 SQLite profile](data/0.20.0-profile-sqlite-mixed-100-r5.json): one recall took 2.464 s wall / 2.432 s CPU; associative matching took 2.101 s inclusive with the same 97 associative and 48,500 episode-feature calls as in-memory. cProfile follows the calling event-loop thread, not SQLite's worker thread; time waiting on async work may be attributed to event-loop functions. It does not measure SQLite worker internals, and inclusive times are not a disjoint storage/cognition breakdown.
* [100 / 20 in-memory profile](data/0.20.0-profile-mixed-100-r20.json): 2,006 observation revisions, 106 semantic revisions and 106 episodes. One recall took 2.329 s profiled, with the same association and feature call counts as 100 / 1 and 100 / 5. This fixture ingests all observation revisions before processing, so it does **not** independently vary semantic revision history; it cannot resolve H1 or historical projection costs.

For uninstrumented comparisons, five fixed, distinct queries were executed per fresh process with cProfile, tracemalloc and SQL tracing disabled. Individual wall and process CPU samples are retained in the [SQLite report](data/0.20.0-timing-sqlite-mixed-100-r5.json) and [in-memory report](data/0.20.0-timing-memory-mixed-100-r5.json). SQLite's median was 0.830 s (range 0.815–0.841 s); in-memory's was 0.775 s (range 0.765–0.803 s). These were sequential runs, not paired or randomized, and five samples do not support p95. Counts, applied correction/withdrawal counts and the fixture's rounded ranked outputs matched. This limited logical comparison is not exact cognitive fingerprint validation.

The profiler now accepts `--backend sqlite` and `--uninstrumented`; each run still uses the original workload and returns individual observations. For example: `uv run python scripts/profile_retrieval.py --backend sqlite --observations 100 --recalls 5 --uninstrumented --output timing.json`. The older reports lack the later backend and profiling flags because they were captured before those flags were added; their fixture and Core source are the same. The script's calls to timers and a wrapper remain present in the uninstrumented mode, but cProfile, SQL tracing and tracemalloc are absent.

Next, construct a fixture that processes successive semantic updates between revisions and compare current and historical queries, then add realistic project and relationship-dense workloads. Measure storage reads and stage counts separately, compare repeated process runs, and validate exact candidate outputs through the independent Bench. These results justify prioritising an association-reuse experiment but do not authorise treating other hypotheses as settled or declaring the 0.20.0 gate complete.
