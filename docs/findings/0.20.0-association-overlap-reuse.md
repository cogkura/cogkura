# Retrieval-scoped seed/episode overlap reuse

This is a second uncommitted development change on top of [episode feature reuse](0.20.0-association-feature-reuse.md), not a release acceptance. The parent commit remains `9745201bfcc5410d678a07737a4c935dd294e5b4`. The first-fix `activation.py` SHA-256 is `f76cfa6de82bd7a0b533a7b15d6279a4bc11647860d5bb04865854689f8c712e`; this candidate's is `5d1414dc120713b39192624ac1322591dede3a58645a6f38fc51503f11874f00`. Profile report commit fields identify the parent, not the modified source.

For each seed, the previous implementation recomputed matching episode features, overlap, sorted candidates and the bounded neighbour list for each semantic candidate. The query, inventory, seed and neighbour limit are fixed within a semantic relevance context; that bounded ordered result is now computed lazily once per seed and reused in the same context. The existing neighbour limit is still applied before semantic-specific filtering. The semantic-specific support/entity checks, weights, path selection and result order are unchanged. The seed instances remain alive while the context and cache exist; no state is shared between retrievals. Empty lists are cached. The change does not prune candidates or introduce cross-retrieval caching.

## Measurements

The unchanged mixed fixture ran on macOS 15.8.1 x86-64, Python 3.11.15, SQLite 3.53.1, with five distinct queries and no profiler, tracing or tracemalloc. Cases ran sequentially in fresh processes, with ordinary host activity and OS caches uncontrolled; fixture construction precedes first recall. The 100-observation prior measurements were retained from the previous session, and the 250-observation prior runs were captured immediately before this change. These five-query samples do not support p95 or a production claim.

The rounded, ordered workload outputs match between each before/after pair. At 250 observations, one in-memory cProfile recall fell from 4.513 s with the first fix to 1.137 s with both fixes. The new profile made five related-list builds and 1,245 `_qualifying_bridge_features` calls, compared with 307,515 overlap evaluations after the first fix. Profiler overhead means these are not uninstrumented latencies; inclusive function times overlap.

The [semantic history workload](../../scripts/run_semantic_history_workload.py) processes each version separately, applying an authoritative correction per subject per subsequent version. It checks current and historical semantic values explicitly and records individual query observations. Its subject-scoped queries are a controlled fixture, not a realistic global workload. Each invocation uses a fresh process; revision depth changes both revision and episode populations, and it does not isolate every factor. The workload and its test are starting points for investigating semantic revision depth; they do not establish complexity or validate all historical boundaries.

A [three-subject, three-version smoke run](data/0.20.0-semantic-history-smoke-memory.json) produced nine semantic revisions and applied corrections `[0, 3, 3]`. Current recall selected `environment-0002`, and historical recall at the initial valid time selected `environment-0000`. The [SQLite run](data/0.20.0-semantic-history-smoke-sqlite.json) matched the rounded ranked outputs. These single samples validate the fixture's basic behavior, not performance or full temporal correctness.

## Validation so far

Offline locked synchronization, Ruff, format check, mypy and the complete Core suite passed (991 passed, 46 skipped). The suite also passed with a disposable local PostgreSQL 14.18 memory database (1,031 passed, 6 skipped; source/admin configurations were not supplied). A regression compares the entire inspection result to a run with related-list reuse disabled, using a neighbour limit of two, and checks that reuse is per seed and per retrieval.

In an independent same-environment Bench run on Python 3.12.13, all 393 query fingerprints and complete retained query/use/metric signatures across 22 frozen profiles match the first-fix candidate exactly; source metrics match excluding latency, and diagnostics parity passed. The [raw candidate report](data/0.20.0-overlap-bench-frozen.json.gz), [full details](data/0.20.0-overlap-bench-frozen-details.json.gz) and [comparison summary](data/0.20.0-overlap-bench-comparison.json) are retained. The raw comparison against unchanged gold still reports `authoritative_corrections_v1/cogkura-correction`; no candidate-specific approval has been applied.

For four independent Bench workloads, the candidate's memory, SQLite and reopened SQLite query fingerprints, full query details, use signatures, non-latency metrics and source assessments match an installed 0.19.6 baseline on the same environment. The [baseline](data/0.20.0-overlap-bench-baseline-local-backends.json.gz), [candidate local-backend report](data/0.20.0-overlap-bench-candidate-local-backends.json.gz) and [candidate four-backend raw report](data/0.20.0-overlap-bench-four-backend.json.gz) are retained. Within the candidate's raw four-backend comparison, mini and persistent inhibition matched across memory, SQLite, reopened SQLite and PostgreSQL; a PostgreSQL mini repeat also matched. The correction and source workloads differ from memory at `ac-q-c03`, `sm-contested` and `sm-evidence-cap` across the other three backends, so the raw backend gate fails. These are the same query identities flagged in earlier 0.19.6 reviews, but previous approvals do not transfer to this candidate. PostgreSQL source-assessment parity separately passed 191/191 checks; see the [raw source report](data/0.20.0-overlap-bench-postgres-source.json.gz). A passing same-environment comparison is evidence, not candidate approval or completion of the strict release gate.

The released 0.19.6 baseline was also run against the same disposable PostgreSQL instance after the candidate. Across all four workloads and all four backend modes, query fingerprints, full query details, use signatures, non-latency metrics and source assessments match the candidate exactly. Both runs reproduced the same three raw cross-backend query differences and both passed the PostgreSQL mini repeat. The [released four-backend report](data/0.20.0-overlap-bench-baseline-four-backend.json.gz) is retained. This comparison does not authorize a candidate-specific exception or make the raw gate pass.
