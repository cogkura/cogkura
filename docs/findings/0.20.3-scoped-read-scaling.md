# 0.20.3 scoped-read scaling investigation

**Status: the 0.20.2 baseline passed the accepted fixture-specific latency
target; exact 0.20.3 candidate validation remains open.**

The SQLite semantic store's `list()` first calls `_read()` and `_hydrate()` for
the tenant, and only then delegates subject filtering to the in-memory store.
The hydration reads the tenant's semantic memories, evidence, entities and
derivations in batches; historical reads additionally need revisions and
snapshot projections. This establishes a mechanism for tenant-size-sensitive
work even when the returned subject inventory is unchanged. It does not prove
that hydration is the only cause of end-to-end latency growth.

As an initial diagnostic, on 25 November 2026 the existing
`scripts/profile_project_updates.py` workload was run once each at 10 and 50
projects against SQLite on the reference Mac/Python 3.11.15. Each run profiles
three successive historical scoped recalls after a configuration admission,
correction and withdrawal. Median instrumented timings across those three
queries were:

| Measure | 10 projects | 50 projects |
| --- | ---: | ---: |
| Scoped recall pipeline | 52.86 ms | 183.17 ms |
| Semantic-loading calls | 44.43 ms | 191.80 ms |
| Revision-loading call | 6.54 ms | 32.24 ms |
| Candidates in successive queries | 15, 15, 14 | 15, 15, 14 |

Instrumentation wraps nested and repeated calls, so stage durations overlap and
must not be summed or interpreted as exclusive time. These are single-process
instrumented observations, not independent acceptance samples or an Agent SLA.
The exact procedure is `python scripts/profile_project_updates.py --backend
sqlite --projects N --output REPORT`; transient profiler output was not committed.
The 0.20.2 uninstrumented three-process findings remain in
[project workload](0.20.2-project-workload.md).

The same instrumented diagnostic on in-memory storage returned candidate
counts of 15, 15 and 14 at both sizes. Median recall-pipeline times were 9.91 ms
and 11.53 ms; median semantic-loading times were 0.23 ms and 0.61 ms. These
single-process diagnostics were run separately, with other local tests active,
and are useful for attribution rather than a controlled backend benchmark.

On 25 November 2026 the release owner adopted an initial single-Agent reference
gate: 50 projects per tenant and 250 observations per project, including repeated
updates, corrections and withdrawals. For a known project, `prepare_context()`
uses `subject_id`, candidate pool 50 and a 2,048-token budget; on the reference
2018 Mac with Python 3.11.15, warm p95 must be below 2.5 seconds in three
independent processes of 100 preparations each. A median under one second is
preferred, not a release blocker. Incident, migration and historical evidence
must satisfy the established top-ten contract. Correct results and no material
unexpected storage growth are required. If unrelated-project hydration causes
a failure, optimize scoped SQLite reads; investigate other bottlenecks on their
own evidence. This gate is not a hosted multi-tenant guarantee.

The required independent variation of requested-project observations, unrelated
semantic inventory, revision depth, and shared relationships and evidence is
still outstanding, as are CPU/memory, complete `prepare_context()` measurements
and broader backend comparisons. These initial
measurements do not justify an automatic optimization or establish that current
behavior is acceptable at that scale.

## Baseline workload and protocol

The first 50 × 250 baseline is being built from the installed 0.20.2 wheel with
`scripts/prepare_agent_scale_fixture.py`. It extends the established project
fixture: each project has its architecture and other project events, including
an architecture correction; project 000 also has a three-stage configuration
update, correction and withdrawal. The remaining records are synthetic,
project-specific engineering notes, not 241 independent semantic claims.
Consequently, this fixture exercises 12,500 observations and their derived
episodes, but it must not be represented as covering every possible semantic
inventory, revision depth or shared-evidence distribution at that scale.

After fixture construction completes and the database is closed, make three
identical database copies and run `scripts/measure_agent_scale.py` in three
sequential independent processes. Each process records the subject counts for
review against the required 50 × 250 fixture and
records all 100 fixed-state preparation samples, source and database hashes,
assessment, selected output and top-ten evidence. The previous working-memory
snapshot and separate evidence checks are prepared before timing. No recorded
use or learning mutation is interleaved with timed preparation. Preserve all
runs, including failures. The first run is baseline investigation; an exact
0.20.3 candidate or demonstrably equivalent runtime still requires the stated
candidate-specific validation and review.

### Published 0.20.2 baseline result

On the confirmed 2018 Mac, macOS 15.8.3 and Python 3.11.15, the fixture was
built using the published 0.20.2 wheel (SHA-256
`ad29a8e3ecff445e31b656b3c50d944aae59f789d92026d5411109e2f44f7f92`).
After a clean close, the database was copied three times; each initial copy
had SHA-256 `9f4b1d7caf651dd73426646bfde2dff148b603b3357a52115fb4f73f882dc217`.
The copies contained exactly 50 subjects with 250 observations each, 12,500
episodes, 302 semantic memories, 303 revisions, and 250 entity relationships.
The database held 90,353,664 logical bytes before the reads. Fixture construction
took approximately 646 seconds; this is not an update-latency measurement.

Three sequential processes each made 100 preparations with a known subject,
pool 50, budget 2,048, a fixed evaluation time and a precomputed prior snapshot:

| Process | Median | Nearest-rank p95 | CPU over samples | Peak RSS |
| --- | ---: | ---: | ---: | ---: |
| 1 | 0.586 s | 0.702 s | 57.09 s | 48.3 MB |
| 2 | 0.565 s | 0.661 s | 55.27 s | 49.1 MB |
| 3 | 0.565 s | 0.664 s | 55.47 s | 49.0 MB |

All three stayed below the approved 2.5-second p95 and preferred 1-second
median for this fixture. All recovered the specified incident, migration and
historical evidence within the top ten. The rendered hashes, assessment
representations, and ranked evidence outputs matched across runs; contexts were
equal within each process. Checked table row counts and logical page counts did
not change during the read-only measurements. These count checks are not a full
cognitive-state audit and do not measure growth from subsequent updates.

Raw reports retain all samples, host and module identities, fixture and driver
hashes, result statements, diagnostics and state-table counts:
[run 1](data/0.20.3-agent-scale-baseline-run1.json),
[run 2](data/0.20.3-agent-scale-baseline-run2.json),
[run 3](data/0.20.3-agent-scale-baseline-run3.json).
Peak RSS is the process high-water mark reported in bytes by macOS, not only the
memory used by one preparation. CPU is the process total for the 100-sample loop.

This is evidence for the specified synthetic observation mix, not a general
promise for all 12,500-observation tenants. In particular, varying the unrelated
semantic inventory, history depth and shared relationships independently remains
open. Nor does a read-only page-count comparison establish that update and
processing growth is acceptable. The exact 0.20.3 candidate, required independent
state audit and final acceptance remain outstanding; this baseline does not
transfer a candidate-specific approval.

### Unrelated semantic inventory diagnostic

To vary unrelated semantic inventory while keeping the observation count at
12,500, `scripts/probe_unrelated_semantic_scale.py` updates one existing note
in project 049 and processes that subject with either 50 or 200 explicitly
authoritative facts. Each variant starts from a separate copy of the exact
baseline database; project 000 and the timed query remain unchanged. This also
creates one observation revision, changed evidence and additional history, so
it does not perfectly isolate semantic inventory from those correlated changes.

The original diagnostic processes returned five-sample medians of 0.608 s and
0.674 s for 50 and 200 added memories respectively. A repeated pair using the
final provenance-reporting script returned 0.669 s and 0.661 s. Each variant
retained 50 subjects with 250 observations each, and all incident, migration
and historical top-ten checks passed. Their rendered hashes, assessments and
recorded evidence statements matched the baseline. The initial pair ran while
a small test was also active. These are short diagnostics, not 100-sample gate
runs or enough evidence for a precise latency-growth curve.

The repeat variants contained 352 and 502 semantic memories respectively,
compared with the baseline's 302. Their logical database sizes were 91,099,136
and 93,167,616 bytes versus 90,353,664 bytes before the updates. Each created
one episode-history row, the corresponding 50 or 200 new semantic memories and
revisions, and respectively 55/56 and 205/206 semantic-memory/revision history
rows. A comparison of each additional snapshot for an existing identity against
its last baseline snapshot found that all five existing-memory and all six
existing-revision snapshots differed only in `updated_at` in each repeat
variant. The timed reads did not change the checked row or logical-page counts. This is
not a general storage-growth bound and does not close the update-growth gate.

Raw reports: [50 initial](data/0.20.3-unrelated-semantic-50-initial.json),
[200 initial](data/0.20.3-unrelated-semantic-200-initial.json),
[50 repeat](data/0.20.3-unrelated-semantic-50-repeat.json), and
[200 repeat](data/0.20.3-unrelated-semantic-200-repeat.json). The initial
reports predate the probe-source hash field; the repeats record the exact input
database and probe hashes. The PostgreSQL comparison and the revision-depth, shared-relationship and
supporting-evidence probes follow below.

### Unrelated revision-depth diagnostic

Two copies of the same 12,500-observation fixture received five or 20
successive authoritative corrections and a final withdrawal on one unrelated
project, using existing observations. Each retained 50 subjects and 250
observations per subject. Five fixed-state preparations per variant had medians
of 0.579 s and 0.594 s respectively. The target project's rendered context,
assessment and three top-ten evidence outputs matched the baseline. These are
short diagnostic runs, not p95 acceptance evidence. Raw reports are
[5 corrections](data/0.20.3-unrelated-history-5.json) and
[20 corrections](data/0.20.3-unrelated-history-20.json).

The five-correction variant added 70 revision-history rows and 47 semantic
history rows; the 20-correction variant added 385 and 152 respectively. A
sequential comparison of each snapshot to the preceding snapshot for its
identity found 56 and 341 revision-history rows, and 35 and 110 semantic
history rows respectively, whose only changed field was `updated_at`. The other
changes include revision and status transitions; the comparison does not claim
all such transitions are independently validated. The logical file sizes were
90,906,624 and 92,897,280 bytes, versus 90,353,664 bytes before the updates.
The observed timestamp-only amplification is explained and material to
long-lived deployment planning. After reviewing longer sequences, the release
owner accepted the measured initial-Agent envelope and deferred compaction to
a later Core version; see the [history investigation](0.20.3-history-amplification.md). In particular, existing historical projection code uses
`updated_at`, so suppressing timestamps or snapshots without a temporal-contract
review would be unsafe. This does not establish a universal growth rate.

### Shared-entity relationship diagnostic

On separate copies of the same baseline, an updated observation for the
unrelated project added 50 or 200 edges to the existing shared `memory-store`
entity, using `scripts/probe_unrelated_relationship_scale.py`. Observation
counts remained fixed. The API persists relationships on `observe()`; no
subject-processing call was made in this probe, so it does not establish
cross-subject consolidation correctness for those edges. The variants had
300 and 450 tenant relationships, up from 250.

The five-sample medians were 0.591 s and 0.658 s. Rendered context, assessment
and the required top-ten evidence outputs matched the baseline. Logical sizes
were 90,394,624 and 90,505,216 bytes, and checked read-time table counts did not
change. These short runs do not establish a latency curve or production SLA.
Reports are [50 edges](data/0.20.3-shared-relationships-50.json) and
[200 edges](data/0.20.3-shared-relationships-200.json). They cover one shared
entity and do not replace independent supporting-evidence or PostgreSQL tests.

### Unrelated supporting-evidence diagnostic

Separate copies of the baseline used `scripts/probe_unrelated_support_scale.py`
to revise five or 50 existing notes in project 049 into distinct supporting
episodes for one claim, then process that subject. Both variants kept exactly
250 observations per project and produced one claim with the requested number
of observation-evidence references. Five-sample scoped preparation medians for
project 000 were 0.594 s and 0.604 s. The target rendered context, assessment
and required top-ten evidence outputs matched the baseline. Raw reports are
[5 supports](data/0.20.3-unrelated-support-5.json) and
[50 supports](data/0.20.3-unrelated-support-50.json).

These samples are diagnostic, not an acceptance p95. Revising observations also
changes episode and semantic history, so the experiment does not independently
vary support count without any other state change. It exercises one unrelated
claim and does not establish all shared-support or cross-subject cases.

### PostgreSQL project-fixture comparison

The existing 10- and 50-project update fixture was also run once per size on a
local disposable PostgreSQL instance, using
`scripts/profile_postgres_project_updates.py` and the same instrumented scoped
historical recalls. Median pipeline times across the three recalls were 96.12
and 109.16 ms respectively; median semantic-loading times were 83.81 and
82.30 ms. As in the other diagnostics, wrapped stage times overlap, include
instrumentation and are not controlled acceptance measurements. Each size had
candidate counts 15, 15 and 14. The expected worker-configuration histories,
complete ranked outputs and assessment flags matched the corresponding memory
and SQLite diagnostic outputs in these runs. The local PostgreSQL configuration
and workload are not a hosted-service latency guarantee. The larger 50 × 250
acceptance fixture above was measured on SQLite only.
