# 0.20.2 software-project workload

**Status: scoped project retrieval selected for the initial Agent; broader
workload assessment remains open.**

The existing heterogeneous project fixture was run with ten projects and five
relationships per project. In-memory and SQLite runs each produced 90 episodes,
60 semantic revisions, 50 relationships and ten applied corrections. The
ranked statements and rounded scores matched for all five existing current,
factual-time historical, incident, migration and broad queries. Individual
single-run wall times and full recorded outputs are retained in
`data/0.20.2-project-baseline-{memory,sqlite}.json`.

This comparison does not provide explicit expected evidence for each question,
full diagnostics or knowledge-time history, nor does it add the design's
multi-session updates, withdrawals and shared-evidence cases. The expanded
workload and its correctness assertions are still required; no performance
threshold is inferred from these single observations.

The named incident, migration and historical-architecture queries did not show
an incident statement, migration statement or prior `postgres_primary` value in
their recorded top ten results. This is an observation from the existing
fixture, which did not define query-specific expected-evidence assertions; it
is not yet a classified correctness failure. The expanded workload must define
those expectations independently and investigate the results before the gate
can pass. Cross-backend agreement alone does not establish relevance.

A one-project memory run of the same heterogeneous fixture did include the
prior `postgres_primary` value in the historical top ten, the incident episode
in the incident top ten, and migration evidence in the migration top ten. Its
raw output is `data/0.20.2-project-baseline-memory-single.json`. At ten projects,
other projects' storage decisions occupy much of the same top-ten output. This
suggests a candidate-competition effect worth investigating, but the paired
runs alone do not establish its cause. Any expectations and supported workload
scope need explicit review before changing retrieval behavior.

An unscoped diagnostic repeated the ten-project fixture with a result limit of
1,000. The specifically named current architecture, historical architecture,
incident and migration evidence appeared at ranks 1, 12, 26 and 27 respectively
on both memory and SQLite; 60–62 results were returned per query. The complete
recorded rankings matched across backends, and their first ten matched the
corresponding original top-ten results in these runs. Reports and the
reproducible diagnostic are `data/0.20.2-project-depth-{memory,sqlite}.json`
and `scripts/probe_project_rank_depth.py`. This locates the evidence in the
larger unscoped result set and demonstrates a top-ten relevance limitation in
this fixture. It does not establish the desired Agent behavior, guarantee that
other limits preserve a prefix, or justify a retrieval-policy change.

An additional ten-project probe supplied `subject_id="project-000"` to the
four project-specific queries, leaving the broad query unscoped. The prior value,
incident episode and migration evidence appeared in the respective top tens;
all five ranked outputs matched between memory and SQLite. The reproducible
probe is `scripts/probe_project_subject_scope.py` and reports are
`data/0.20.2-project-scoped-{memory,sqlite}.json`. This is a different API
request from the unscoped baseline and depends on the caller knowing a subject;
it does not prove that unscoped behavior meets the eventual workload's goals.

A regression now specifies expected statements for the scoped current and
factual-time historical architecture questions, the incident and migration
questions, and the broad question. It checks their presence in the top ten
and compares the complete recorded rankings across memory and SQLite. This
protects the scoped scenario; it does not change unscoped rankings, exercise
knowledge-time reconstruction, or supply the expanded
multi-update and withdrawal workload.

The product decision for 0.20.2 is to retain Core's existing ranking. The
Agent will resolve the project name and supply the appropriate `subject_id`;
the unfiltered incident and migration ranks of 26 and 27 are a documented
limitation, not a release blocker. The existing scoped regression explicitly
requires the incident and migration evidence in the first ten results on both
tested backends. Project-name resolution belongs to the Agent and is not
implemented by this Core test.

A separate lifecycle regression now covers multiple sessions, an incident,
a future-effective correction and a subsequent withdrawal. It checks the
expected semantic values and source provenance at matched and independently
varied knowledge and factual times, including after later modifications. The same assertions
passed on in-memory storage, SQLite after reopen and PostgreSQL. This is a
focused lifecycle case, not a substitute for the larger workload's latency,
diagnostic and growth assessments.

The lifecycle regression also runs the same correction, withdrawal, historical
recall and provenance checks with subject-scoped processing, on memory and
SQLite and PostgreSQL. A separate SQLite regression checks that a scoped unrelated update
leaves another subject's existing episode, semantic and semantic-revision
history rows and current episode and revision lists unchanged. This is a
focused example rather than a general guarantee for shared or cross-subject
evidence.
The scoped lifecycle also passed against the official-origin `64f85f7`
candidate and a disposable local PostgreSQL database on CPython 3.11.15.
