# 0.20.2 retrieval performance repeatability

**Status: in progress; release gate not satisfied.** The local working-source
timing batch passes, but the full state check and frozen candidate remain open.

`4c53eb6a5f77cb9c275c7b39529f08fac7e809b1`. The mixed workload has five

## PostgreSQL exploratory baseline

Against a disposable local PostgreSQL 14.18 instance over a Unix socket, three
100-observation processes produced warm medians of 0.481 s, 0.472 s and
0.472 s; their recorded outputs and selected fixture state matched. The three
raw reports are `data/0.20.2-baseline-postgres-100-run{1,2,3}.json.gz`. The
in-memory and SQLite targets are not applied to PostgreSQL. Larger sizes,
remote network overhead and candidate comparisons remain unmeasured.

The local machine identifies as a MacBookPro15,2 with a 2.3 GHz quad-core Intel
Core i5 and 8 GB RAM. Its reported macOS, Python and SQLite versions match the
metadata in the earlier 0.20.1 acceptance report. That metadata alone does not
independently establish physical host identity. On 22 November 2026, the user
confirmed that this is the same physical 2018 Mac used for the 0.20.1 retrieval
acceptance measurements. The macOS system profiler could not read cache sizes in the sandbox,
so they are not reported.

The profiling harness has since been extended to reread the fixture's recorded
observation-revision values, semantic values and object counts *after* the timed
operations, and to reject a run if those values change. No additional state reads
are introduced before the first timed recall. The review tool reports whether
all input reports contain this post-measurement check; earlier baseline reports
predate it and remain preserved as recorded. The check covers these selected
values, not complete activation, learning, inhibition or other cognitive state,
so full state verification and candidate measurements remain open.

A fresh three-process 100-observation batch using the enhanced harness passed
on both backends. Warm medians were 82.7, 82.2 and 82.5 ms in memory and
121.1, 122.6 and 122.5 ms on SQLite. Each run passed the selected post-run
fixture-state check, and recorded outputs and selected state matched the earlier
100-observation baseline for its backend. The reports are
`data/0.20.2-postcheck-{memory,sqlite}-100-run{1,2,3}.json.gz`. The remaining
sizes have not been rerun as performance measurements with this added check;
full cognitive state still requires verification.

## Separate cognitive-state audit

The profiling harness now has an opt-in `--cognitive-state-audit` mode. It
snapshots data immediately before the recall sequence and compares it with a
fresh read afterwards, detaching nested values so mutation cannot change both
copies. It covers the fixture's current observations and revisions, episodes,
semantics and revisions, relationships, dynamics, activation and learning
reinforcement traces, global-context learning state, associations, and
inhibition for the fixture's current memory identities. Trace reads are
bounded at 2100-01-01 UTC. An injected recorded access demonstrates that the
audit fails when activation changes.

These additional reads happen before the first recall, so audit timings are
not performance measurements; the repeatability review rejects audit-mode
reports. The audit does not establish equality for every historical snapshot,
learning context, inactive identity or other store-internal state, and it does
not add the before-state check to the earlier timed runs. The full per-run
release gate therefore remains open.

With the in-progress 0.20.2 source, one audit for each of the 100, 250 and
1,000 observation memory and SQLite fixtures passed, using 100 recalls each.
Their recorded counts, selected fixture values and
ranked outputs matched the first 100 outputs of the corresponding 0.20.1
baseline run. The two backend audit batches ran concurrently with each other
and with the test suite, so their timing samples are not valid performance
measurements. Reports are
`data/0.20.2-cognitive-audit-{memory,sqlite}-{100,250,1000}.json.gz`.

## 0.20.2 working-source timing batch

On the confirmed reference Mac, the 0.20.2 working source was measured
with three independent, sequential, uninstrumented runs per backend and size.
The candidate is not frozen. The completed smaller groups are:

| Backend and observations | 0.20.1 warm medians (ms) | 0.20.2 working-source warm medians (ms) |
| --- | --- | --- |
| Memory, 100 | 85.19, 87.32, 85.98 | 80.07, 76.58, 76.57 |
| Memory, 250 | 222.04, 222.20, 224.79 | 202.47, 203.36, 201.97 |
| SQLite, 100 | 125.43, 126.91, 125.87 | 115.96, 116.26, 116.16 |
| SQLite, 250 | 322.55, 322.51, 321.03 | 304.72, 302.22, 303.07 |

Every run in these groups met the one-second target, and the recorded ranked
outputs and selected fixture state matched their baseline. Each run also
passed the selected post-run fixture-state check; the broader per-timed-run
cognitive-state comparison remains open. At 1,000 observations, the three
memory p95 values were 1.204, 1.273 and 1.160 seconds, each under the two-second
target, compared with 1.327, 1.345 and 1.296 seconds for the baseline. Their
recorded outputs and selected fixture state matched the baseline and each passed
the selected post-run check. At 1,000 observations, the three SQLite p95 values
were 1.757, 1.718 and 1.717 seconds, compared with 1.840, 1.924 and 1.931
seconds for the baseline. All three met the two-second target and their
recorded outputs and selected fixture state matched the baseline. No run was
discarded. Raw reports are retained as
`data/0.20.2-candidate-{backend}-{size}-run{1,2,3}.json.gz`.

These working-source results establish no material timing regression in the
measured local fixture. The separate candidate measurements below address
timing, while complete per-run cognitive-state comparison remains open. Host load is recorded before each
fixture and is contextual, not a complete record of competing activity.
