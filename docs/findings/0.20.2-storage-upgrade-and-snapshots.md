# 0.20.2 storage upgrades and snapshots

**Status: partial; release gate remains open.**

A regression creates a two-tenant SQLite database in separate Python processes
using the actual `v0.19.5` and `v0.19.6` source trees extracted from Git. Each
fixture contains observations and revisions, episodes, semantic memories,
relationships, activation references, learning and association records,
forgetting dynamics and inhibition traces. The current Core opens each database twice, preserving episode and semantic identities and
values, together with the exact retained observation revision identities and
source versions and the stored cognitive-state rows. Public learning and
inhibition reads also recover the expected data, with both pre-existing tenants
marked as having incomplete history ordering. Before the successful upgrade, an injected failing migration rolled
back all newly applied migration records and history tables; both databases
then upgraded successfully. A subsequent write creates a non-null episode
snapshot, and the other tenant's episode identities remain intact. Both cases passed locally.

The initial checks above are source-based. The wheel checks described below
cover installed prior releases. Neither variant covers all revision and cognitive-state variants,
all snapshot operations, other
upgrade failure modes, full snapshot growth, or the final frozen candidate.
Those gates remain open.

Prior-release PostgreSQL source fixtures for 0.19.5 and 0.19.6 were created
in separately generated temporary databases on local PostgreSQL 14.18. The
upgrade tests compared stored cognitive rows, observation revisions, episodes
and semantics, public-store learning and inhibition, and tenant-scoped history
coverage. An injected migration failure rolled back the pending migrations;
rerunning migration succeeded and was idempotent. A new post-upgrade episode
snapshot round-tripped, while the other tenant remained intact. The databases
were dropped after testing. These checks do not provide comprehensive atomicity evidence.

The PostgreSQL-marked Core suite, including these upgrade and concurrency
and snapshot rollback regressions, passed 58 tests with 6 skips on the isolated
local instance with the published and provisional wheels available.

## Initial SQLite snapshot-size observations

The existing five-revision mixed fixture was measured after close at two sizes.
At 100/250 observations respectively, the complete database and SQLite backup
were 3,559,424/8,167,424 bytes. Episode history contained 106/256 snapshots
averaging 1,737/1,736 payload bytes; semantic history contained 203/503
snapshots averaging 2,155/2,154 bytes; semantic revision history contained
206/506 snapshots averaging 2,432/2,420 bytes. There were six relation-history
rows in each fixture. Raw reports include row counts, total UTF-8 payload bytes,
SQLite `dbstat` page allocations by object, database and backup sizes:
`data/0.20.2-snapshot-growth-sqlite-{100,250}.json`.

These are synthetic fixture sizes, not marginal costs or a general scaling
model. Database and backup totals include all retained data and indexes, not
just snapshots. Repeated reinforcement, WAL peak size, read/RSS overhead,
retention interactions and larger fixtures still require assessment; no
snapshot pruning is implied by these observations.

In separate reruns adding per-identity counts, each episode had one history
record in these fixtures. Semantic histories had one or two records per memory
(mean 1.97/1.99 at 100/250); semantic revision histories had one or two per
revision (mean 1.94/1.98). Reports with the distributions are retained as
`data/0.20.2-snapshot-growth-sqlite-{100,250}-v2.json`. These counts do not
measure repeated reinforcement beyond the fixture's operations.

## Snapshot transaction failure injection

On SQLite and PostgreSQL, parameterized tests inject a failure when inserting
semantic-memory or semantic-revision history during an authoritative correction
or withdrawal. Corrections also inject a failure during relation-history
insertion. The checked semantic state, history and ordering records remained
unchanged across each failed semantic transaction, and a retry succeeded.
PostgreSQL episode-history insertion failure likewise left the episode and
ordering state unchanged; its earlier observation ingest remained committed
and retrying episode encoding succeeded. The existing SQLite episode snapshot
failure test also verifies episode rollback. These tests do not imply that
`Memory.process()` is a single transaction, nor do they cover every possible
failure point or tenant-clearing behavior.

A two-tenant clear regression additionally verifies that episode, semantic and
revision history for the cleared tenant is removed while the other tenant's
corresponding snapshots remain unchanged. It passed on in-memory, SQLite and
PostgreSQL. This does not claim tenant clear is a single cross-store transaction.

For the upgrade runs, `v0.19.5` resolved to
`13ad7336de1e8be4eba95fbd673ccb448c612d03` and `v0.19.6` resolved to
`9745201bfcc5410d678a07737a4c935dd294e5b4`; the current checkout was
`a62196b8ec37ca07f36900ea6173514083ae7d40`. The test requires those tags to
be available and skips explicitly when they are not.

## Repeated reinforcement probe

A separate 100-observation mixed fixture received five additional observations
supporting an existing uncorrected semantic value. Each measurement times the
complete observation-and-`process()` operation, which processes the tenant's
memory; it is not an isolated single-memory write. Each pass reported 94
semantic reinforcements and one semantic update. Episode-history rows grew from
106 to 111, semantic-history rows from 203 to 688, and semantic-revision-history
rows from 206 to 736. Per-pass elapsed times were 0.291, 0.332, 0.317, 0.300
and 0.335 seconds. After close the complete database and backup were each
7,852,032 bytes, compared with 3,559,424 bytes in the separate initial 100-item
fixture. The full per-pass observations are retained in
`data/0.20.2-snapshot-reinforcement-sqlite-100.json`.

This demonstrates substantial history amplification for repeated tenant-wide
processing in this synthetic fixture and is an open scaling and retention
finding. The comparison includes all added observations, state, pages and
indexes; it is not a precise attribution of the file-size increase to snapshot
payloads. Investigate expected Agent processing frequency, larger fixtures, RSS,
retention and backup implications before deciding whether the measured effect is
acceptable. No pruning or optimization has been introduced.

Code inspection is consistent with this amplification: reconciliation builds a
plan containing the tenant's current semantic projections and revisions, and
the in-memory semantic store records a history entry for each planned memory
and revision. Persistent stores implement their own or hydrated versions of
that write path. A safe reduction would need to preserve observable timestamps,
historical ordering and cross-backend behavior; these measurements do not by
themselves justify removing or deduplicating snapshots.

The same SQLite fixture and migration checks were also run with the published
0.19.5 and 0.19.6 universal wheels installed into separate dependency-free
virtual environments. The wheels were downloaded from PyPI, checked against
PyPI's SHA-256 metadata, and verified again by the opt-in test:

- 0.19.5: `29ec696acba22b9752948d8f394551066ad1038989e0a30244162a6ed7460fe0`
- 0.19.6: `862d1a08b3d939bc1eea81d883c03315a30509c6779e12abec6f5fb85d8252d4`

Both installed-wheel cases passed, along with both tagged-source cases. The
upgrade itself used the current source checkout; repeating it with the exact
frozen 0.20.2 distribution remains required. The offline test is enabled by
setting `COGKURA_RELEASE_WHEEL_DIRECTORY` to a directory containing the verified
wheels; the test skips those two cases when the wheels are unavailable.

## Retention boundary

A SQLite regression writes an observation in full-retention mode, then updates
it in hash-only mode. The new content marker was absent from the tested current
and historical observation content and snapshot payloads, while the original
full-retention content remained in its earlier episode snapshot. Hash-only mode
retained the new observation's supplied metadata, as specified by the retention
implementation. Changing the mode therefore does not retroactively minimize old
snapshots and is not a general metadata-redaction policy. Tenant clear removed
the tested logical history rows; it is not a secure-deletion test and does not
remove copies in prior backups. Applications must account for retained snapshot
content, metadata and backups when selecting a retention policy.

A separately constructed 100-observation fixture repeated the five updates
with `process(subject_id="service-0006")`. Each pass reported one semantic
reinforcement; semantic-history rows increased from 203 to 208, revision-history
rows from 206 to 211, and episode-history rows from 106 to 111. Complete
observe-and-process timings ranged from 0.108 to 0.115 seconds; the final
database was 3,633,152 bytes. See
`data/0.20.2-snapshot-reinforcement-scoped-sqlite-100.json`.

This supports the interpretation that the amplification depends on the scope
of processing in this fixture. Subject-scoped and tenant-wide processing are
different requests: using the former is appropriate only when the application
knows the affected subject and does not require processing other subjects. It
is not a general replacement for tenant-wide processing, and the tenant-wide
retention and Agent-impact finding required the subsequent scope decision below.

The same five-update probe at 250 base observations reinforces the scaling
concern. Tenant-wide processing reported 244 semantic reinforcements on every
pass; semantic-history rows rose from 503 to 1,738, semantic-revision-history
rows from 506 to 1,786, and the complete database and backup were each
18,718,720 bytes after close. Observe-and-process times ranged from 0.603 to
0.640 seconds. The separately constructed subject-scoped fixture reported one
reinforcement per pass; the corresponding history counts were 503 to 508 and
506 to 511, database and backup were 8,245,248 bytes, and pass times ranged
from 0.147 to 0.164 seconds. Both started with 256 episode-history rows and
ended with 261. Reports are
`data/0.20.2-snapshot-reinforcement-{,scoped-}sqlite-250.json`.

The Agent product decision is to use subject-scoped processing by default and
reserve tenant-wide processing for explicit maintenance. Before the 0.20.3
freeze, scoped processing must be validated for correctness and unrelated
updates must not create unexplained historical state for unaffected subjects.
The scoped project lifecycle and SQLite history-isolation regressions provide
focused coverage; shared evidence and other workloads still require validation.
The working Core source was 0.20.2 with only its version string changed from
the 0.20.1 runtime. The probe and workload script SHA-256 values were
`f712db1bb6aa43695c07fbf92d8085ad2b03ce014ad798c3e04822eb1b4a4aa7`
and `7328ec2eb9ef302e914951a0f17463a7226df64b0549b8007063765a11742830`.

For comparison, the separate 250-item initial fixture occupied 8,167,424 bytes.
In this synthetic sequence, an Agent that processes the entire tenant after each
small update would retain and back up substantially more data than one whose
application can correctly restrict processing to the affected subject. These
figures include all database pages and are not a prediction of production growth;
actual impact depends on Agent processing policy, memory contents, retention and
backup frequency. Subject scope cannot replace tenant-wide processing when other
subjects need work. No snapshot pruning or change to cognitive behavior has
been made.

**0.20.2 disposition for the initial Agent:** the user explicitly selected
subject-scoped processing by default, with tenant-wide processing as an
explicit maintenance operation. For callers that know the affected subject,
the measured tenant-wide amplification is a documented limitation of the
maintenance operation rather than a demonstrated 0.20.2 blocker. Applications
must still select tenant-wide processing when it is needed for correctness.
The user also made scoped correctness and the absence of unexplained history
for unaffected subjects mandatory before the 0.20.3 freeze; current focused
regressions do not establish those properties for every shared-evidence case.
This disposition neither approves a retention policy nor predicts long-term
growth or backup costs.

environments, with PostgreSQL dependencies supplied by the test environment.
Copies of both databases were upgraded using that provisional 0.20.2 wheel in

The source-based migration failure, retry and new snapshot checks also passed

The released-source and published-wheel fixtures now also create an independent
tenant with an authoritative correction followed by withdrawal under each
0.19.x release. The resulting three semantic revisions, their statuses,
validity intervals and retained revision snapshot payloads were identical after
upgrade on SQLite and PostgreSQL. Copies upgraded in two fresh processes with
the installed provisional 0.20.2 wheel also retained those fields. All eight
backend, release and fixture-kind cases passed. This verifies the tested
transition history, not every possible legacy history or the final candidate.

An installed-candidate full-suite run initially failed both published-wheel
PostgreSQL upgrade cases because the test's dependency path placed the
candidate package ahead of the old installed wheel. The fixture's version
assertion caught this: the attempted old fixture imported 0.20.2. The harness
now puts the old wheel's environment first, and all four PostgreSQL upgrade
cases pass against the installed candidate. In a subsequent suite run reusing
the same disposable database, two semantic-store tests failed because their
fixed tenant retained state from the earlier run. Those tests now use unique
tenants and clean up only their own data; the two tests passed twice against the
same previously used database. These were test setup failures, not discarded
product failures; the corrected full suite was rerun on a fresh database.
Against the successor installed Git candidate, the fresh-database full Core
suite passed 1,125 tests with six skips, including the released-wheel checks.
