# Current-state semantic admission lookup

This uncommitted performance candidate is measured on top of the separately retained [history correctness candidate](0.20.0-history-correction-investigation.md). It is not a release acceptance. The preceding [profile](0.20.0-scaling-followup.md) identified a repeated linear search through scored results for each semantic candidate.

The candidate lazily constructs a retrieval-local dictionary of activations by identity when the first eligible semantic candidate needs it. `setdefault` retains the first matching result, preserving the previous `next` behavior for duplicate identities. Missing identities, threshold checks, candidate order, soft-admission caps and sorting are unchanged. A regression exercises duplicate order and compares the complete inspection output to the original linear lookup on the same state. The cache does not persist between retrievals.

## Independent measurements

Using the original mixed fixture, the correctness-only source patch was measured first, then this candidate. The fixed query sequences, fresh processes, CPython 3.11.15 and same host apply as described in the earlier findings. No profiler, SQL tracing or tracemalloc was active for the primary samples; the first query follows fixture construction, and host activity and OS caches were not controlled. Each backend/size has five samples, insufficient for p95. Ordered results rounded to eight decimal places matched the corresponding before run for all queries.

## Validation and open gates

The final combined candidate passed the Core suite without PostgreSQL (999 passed, 47 skipped) and a PostgreSQL-memory-enabled full run (1,039 passed, 6 skipped); the later-added SQLite legacy-reopen test also passed separately and in the final local suite. Offline locked synchronization, Ruff, formatting and mypy passed. The source and benchmark patch hash above identifies the candidate implementation; local tests and documentation are not part of that source patch.

Against the correctness-only candidate, independent Bench on Python 3.12.13 reports identical complete query/use/metric signatures and all 393 frozen-query fingerprints across 22 workload profiles. Across the four tested backend modes and four workloads, query details, fingerprints, uses, non-latency metrics and source assessments also match the correctness-only candidate; PostgreSQL mini repeat matched. PostgreSQL source parity passed, meaning its output matched the in-memory source output. The [comparison summary](data/0.20.0-admission-bench-comparison.json), [raw frozen report](data/0.20.0-admission-bench-frozen.json.gz), [full frozen query details](data/0.20.0-admission-bench-frozen-details.json.gz) and [raw four-backend report](data/0.20.0-admission-bench-four-backend.json.gz) are retained.

These equivalence results do **not** mean that the combined candidate passes release acceptance. The correctness change's three changed frozen query signatures and source-transition differences remain subject to the review described in the [correctness findings](0.20.0-history-correction-investigation.md). The user chose to expose both correction and withdrawal transitions; the frozen source fixture still expects withdrawal alone and reports 190/191 source checks, so the raw gate fails. No source gold, old approval manifest or numeric tolerance has been changed or carried forward.
