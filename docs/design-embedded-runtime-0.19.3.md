# Embedded runtime (0.19.3) — design

`EmbeddedMemory.open(path)` opens one Cogkura-owned SQLite database and constructs a `Memory` with every persistent storage protocol backed by the same explicitly owned worker and connection. It uses only the standard library. Opening creates or migrates supported schemas before returning; incompatible, unavailable or locked databases fail rather than silently falling back to in-memory stores.

The returned owner exposes `.memory` for the existing cognitive API and `await close()` for shutdown. It also supports `async with await EmbeddedMemory.open(path) as memory:`. Closing is idempotent, prevents new work, drains accepted work and closes the connection and worker. If construction fails after opening the database, the owner closes it before propagating the failure. An already acquired `Memory` does not own the database and must not be used after closing. Reopening is a new owner, not restarting a closed one.

The caller may pass existing `Memory` configuration and algorithm options through `open`; storage and semantic-inspection overrides are rejected so an embedded instance cannot silently mix persistent and transient stores. Working-memory snapshots remain transient. A non-empty filesystem path is required; an ephemeral `:memory:` database is outside this durable runtime. The parent directory must exist. No Core version, cognitive algorithm, ranking or default changes.

SQLiteStorage provides WAL, foreign-key enforcement, a finite configurable busy timeout and serialized writes. One owner serializes its own operations on a worker; independent owners and processes coordinate through SQLite locks. Separate connections can read committed data while another holds a write transaction; writers wait up to the busy timeout and then receive `StorageError`. Startup migration is serialized. Cancellation of an already submitted operation leaves its commit outcome uncertain; close drains the worker. Store-level transactions remain the guarantee; `Memory.process()` is not a single transaction.

Validate creation and reopening, complete store wiring including provenance and cognitive-state persistence, configuration forwarding and rejection of store overrides, context-manager and explicit close, close after errors, concurrent close and cancellation, older schema migration, missing/unavailable/incompatible databases, bounded lock failure, independent readers/writers, and a fresh-process reopen. Verify SQLite storage without the PostgreSQL extra and run Core gates on Python 3.11–3.13. Performance, process-crash recovery and backup/restore hardening remain 0.19.4; this milestone does not promise cloud sync, file encryption, cross-backend export, or a multi-stage atomic transaction.

## Implementation findings

The managed runtime and context-manager interface are implemented. Tests cover full-bundle restart, unchanged retrieval and learning, migration, explicit and context-managed close, cancellation and draining, startup cleanup, invalid paths and options, lock timeouts, reads during a write reservation, a fresh-process reopen and concurrent independent-process writes. The full Core suite passed with PostgreSQL 16 on Python 3.11–3.13: 1,002 tests per runtime, no skips. Ruff, formatting and mypy passed on all three. A clean Python 3.12 environment installed the built wheel without optional dependencies and opened and reopened a local database.

The existing tenant-wide semantic inventory materialization and cognitive-state scans remain known performance limitations. Recovery after abrupt process termination, backup consistency and larger workload validation are not claimed by these results and remain 0.19.4 work.
